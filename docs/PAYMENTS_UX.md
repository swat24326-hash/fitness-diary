# Оплата у стойки — эргономика (менеджер)

**Актуально:** 2026-11-01  
**Статус:** 📋 сценарий UI (код ещё нет). Канон полей — [PAYMENTS_DOMAIN.md](./PAYMENTS_DOMAIN.md).  
**Кто продаёт:** менеджер по продажам (основной). Админ и управляющий своего клуба (`/club/sales`) — те же шаги (день они уже пишут). Тренер **не** принимает оплату. Целевая политика «тренер не меняет сроки/лимит абона» — отдельная ставка, не этот экран.  
**Железо:** банковский терминал **MF960L** + фискальный **АТОЛ 25Ф**. Сейчас: карта → пробив в 1С/кассе. Цель: Ядро → АТОЛ; Excel не каждый день.  
**Стойка только онлайн** (клиент + правки абонов + новый абон + payment — **одна** серверная операция; две записи в очередь уже роняли абон — INC-2026-10-31-03).

## 1. Ситуация → польза

| Ситуация | Сейчас | С оплатой в Ядре |
|----------|--------|------------------|
| Клиент у стойки купил / продлил абон | Терминал + 1С + вечером Excel | Менеджер бьёт в Ядре → клиент, абон, деньги, день |
| Нужна акция месяца | Шт. акции руками в отчёте | Ссылка на акцию на платеже; шт. в дне — по правилам §5.1 |
| Вечер | Свести файл и CRM | Список оплат = правда денег; файл — догонка |

**Вердикт продукта:** делаем, когда владелец скажет **«берём платежи»** ([PATH_TO_GOAL.md](./PATH_TO_GOAL.md) §4, ставка **6**). Этот файл — сценарий стойки, **кода ещё нет**. Касса АТОЛ — ставка **10**, после живого `payment` и ворот «работает идеально».  
Буквы фаз в §6 (C0…E) — фазы **экрана**. Их **не** путать с A–E в [PAYMENTS_DOMAIN.md](./PAYMENTS_DOMAIN.md) (A модель, B таблица, C список UI, D облачная касса, E железо).

Списание занятий и турникет — **не** этот экран (§7, §9, §10).

## 2. Принципы эргономики

1. **Одно место у стойки** — день отчёта → **«Принять оплату»**.
2. **Оплата = связка** — клиент + (почти всегда) абон + `payment`.
3. **История абонов на виду** — до подтверждения оплаты менеджер видит все пакеты клиента (по залу продажи — развёрнуто; другие залы — кратко) и может **сразу править** остаток/даты/комментарий и **перенести хвост занятий** в новый абон (§3.1).
4. **Минимум полей на деньги** — сумма (прайс), сегмент, акция; пакет — тип/срок/лимит с учётом переноса.
5. **Карта и чек** — MF960L отдельно; АТОЛ позже из той же кнопки.
6. **Не смешивать** — деньги / визит / дневник / часы ЗП (§9). Перенос остатка — правка **абонов**, не отдельный «фейковый» платёж.

## 3. Главный сценарий — продажа / продление (ПЗ или АЗ)

1. **«Продажи» → отчёт за сегодня**.
2. **«Принять оплату»**.
3. **Клиент**
   - поиск как в «Клиентах»: цифры → № карты; телефон — отдельный режим;
   - нашли → карточка;
   - архив → «Вернуть» / «Вернуть и абон»: снимает архив клуба, причину и «вернётся позже», открывает **зал этой оплаты**; другие закрытые залы сами не оживают; баллы лояльности **не** возвращаются;
   - несколько живых с одной картой → «Дубли карты», без автосоздания;
   - нет в базе → «Новый» здесь же (истории абонов ещё нет — шаг 4 короткий).
4. **История абонементов + правки (§3.1)** — **обязательный экран/блок**, не опция «зайди в карточку потом».
5. **Что продаём (новый / следующий пакет)**
   - MVP: **ПЗ** | **АЗ** (ТЗ и **доп.** — очередь 2);
   - ПЗ: тренер обязателен («Не назначен» не использовать); чужой тренер на карточке → спросить перевод;
   - АЗ: направление + срок/занятия;
   - **продление** = следующий абон этого зала (часто старт впереди → «Ждёт старт»), с учётом переноса остатка с шага 4. Это **не** жест импорта «Уже в базе»;
   - **не** бить `payment` на **БЗ / пробную ПНК**.
6. **Сумма** — прайс ПЗ/АЗ; `memberships.paid_amount` = цена **продаваемого** пакета; `payment.amount` = факт денег. Перенесённые занятия **не** увеличивают сумму чека сами по себе (это не допродажа, а учёт хвоста). Dop — очередь 2.
7. **Сегмент НК / ДК / УК** — подсказка `classifySaleClientSegment` (как импорт), не чип воронки:
   - холодный УК → горячий УК → ДК → НК; оба УК → `uk`;
   - ДК = живой абон **этого** зала на дату; абон «с сегодня» для подсказки не ДК;
   - НК = не было законченных тренировок; первая платная после БЗ = НК;
   - менеджер может сменить. Метка **дня**, не статус карточки.
8. **Акция** — ссылка на платеже; шт. акции в дне в v1 **ручные**.
9. **Комментарий** (виден на успехе и в карточке):
   - короткий текст на **платеже** (`payment.note`) и/или на **новом абоне**;
   - при переносе остатка программа **сама предлагает** черновик вроде: «Перенесено 2 зан. с абона до ДД.ММ» — менеджер правит;
   - комментарий обязателен, если сделали перенос или ручную правку лимита старого пакета (чтобы через месяц было понятно).
10. **«Оплата»** — одна операция на сервере: правки старых абонов (если были) + новый/продлённый абон + `payment` (+ клип ПЗ). Карта MF960L; АТОЛ позже.
11. **Успех** — клиент · что сделали со старым пакетом · новый абон (N/M с учётом переноса) · ₽ · сегмент · акция · комментарий. Не обещать LTV.
12. День — по **§5.1**.

### 3.1. История абонов, перенос остатка, правка на месте

**Зачем:** у клиента часто «осталось 2», их нужно учесть в следующем пакете, не теряя след в CRM.

**Что видит менеджер** (после выбора клиента, до денег):

| Блок | Содержание |
|------|------------|
| Список абонов **зала продажи** | Все пакеты (живые, «ждёт старт», законченные): тип, даты, N/M или остаток, цена, тренер/направление, пометка |
| Другие залы | Компактно: «ещё ТЗ · до …», «АЗ Бокс · 3 ост.» — без ухода с экрана |
| Действия на строке | Развернуть → **править** даты, `total` / остаток, `paid_amount`, комментарий абона; закрыть/исчерпать пакет |

**Перенос остатка** (частый жест при продлении ПЗ/АЗ):

1. Подсветка: «На текущем абоне осталось **K** занятий».
2. Кнопка **«Перенести K в новый»** (или ввести другое число ≤ K).
3. Эффект в одной операции с оплатой:
   - у **старого** абона: остаток обнуляется / пакет помечается закрытым по занятиям (как договоримся в домене: `used = total` или явный конец) + запись в комментарии старого;
   - у **нового**: `total_trainings` = купленные + перенесённые (или отдельное поле учёта — в MVP достаточно увеличить лимит и написать в note, **без** второго `payment` на «хвост»);
   - в `payment.note` / note нового абона — текст переноса.
4. Менеджер **до подтверждения** видит итоговый N/M нового пакета и может поправить цифры вручную.

**Правила:**

- Перенос — **не** списание визита и **не** платёж; дневник старых тренировок остаётся на старом `membership_id`.
- Нельзя перенести больше, чем осталось; нельзя «нарисовать» остаток без истории.
- ТЗ (только срок) — перенос «занятий» не применим; при ТЗ блок истории всё равно виден (сроки/цены).
- Редактирование чужого зала в этом мастере — только просмотр + ссылка «открыть карточку»; правки зала продажи — да, на месте.
- Тот же ledger истории, что в карточке клиента / desk ([AdminDeskMembershipLedger](../src/components/admin/AdminDeskMembershipLedger.jsx) как ориентир UX), не второй «секретный» список.

### ПЗ: lite / клип (актуальный API)

- Без тренера не сохраняем.
- **Lite** (без планшета): в успехе lite-карточка + абон; клипа нет.
- **С планшетом:** успех вызывает текущий **`sale-clips` create** — абон ПЗ **уже создан**, клип сразу `done`, пуш «Новый абонемент», на планшете пакет после Sync. **Не** второй абон и не «заявка без пакета».
- Чужой тренер — только с `confirm_transfer`.
- БЗ / пробная ПНК платную продажу **не** закрывают (`membershipMayCloseSaleClip`).
- Повтор того же пакета в тот же день — без второго абона 0/0.
- Желательна связь `payment_id` на клипе/абоне.

### АЗ: desk

Направление обязательно; multi-hall. Визиты — «Списать занятие», не оплата. Штуки АЗ в матрице дня часто из списаний — оплата **не** должна затирать их вниз и **не** обязанa давать авто-+1 шт. АЗ (иначе двоится с журналом визитов).

### После ПНК

Платный абон = оформление в мастере («Оформлен (ДК)»); `pnk_total` дня (потенциальные) оплата **не** увеличивает. Если уже есть ТЗ/АЗ — карточку не удалять. БЗ ≠ `payment`.

## 5. Вечер менеджера

1. **«Оплаты за день»** — список строк.
2. Хвосты: без карточки / без абона.
3. Excel `31.xlsx` — догонка. **`otchet_pz`** — другой контур (часы), не из оплат.
4. Стратегия: Σ `profit_day`; «Уже купили след.» — по **абонам**, не по чеку. План ДК из закрытий оплата сама не переписывает.
5. Уже закрытые вручную дни сами не пересчитываются.

### 5.1. Что оплата меняет в дне (P0 — иначе день не сохранится)

Живой день продаж: в ячейке зал×сегмент нужны **и сумма, и штуки** вместе (`computeProfitFromMatrix` / импорт так же). Итог = НК+ДК+УК + **dop** − **возвраты**.

| Что | Поведение v1 у стойки |
|-----|------------------------|
| Оплата **ПЗ** (и позже ТЗ) | +₽ и **+1 шт** в ту же ячейку зал×сегмент |
| Оплата **АЗ** | +₽ в ячейку; шт. АЗ — из журнала списаний / ручного ввода; **вниз не затирать** |
| **dop_sum**, **refunds_amount** | Кнопка **не затирает** |
| **pnk_total**, «тренировок за день» | Не трогать |
| Акция на платеже | Ссылка; шт. акции в дне — **ручные**, ≤ потолка ячеек |
| Ошибочный чек | `voided_at` → убрать из сумм (и шт., если добавляли) |
| Возврат денег клиенту | Поле **`refunds_amount`**, не void |
| Кто пишет | sales_manager, admin, supervisor своего клуба |

Позже, когда ledger стабилен, можно сузить «рубли только из payment, шт. иначе» — но **не** ценой сохранения дня без пары шт+₽.

## 8. Короткие правила

- Без `client_id` — явный хвост в дне.
- Списание визита / «Закончить» ≠ `payment`; `payment` ≠ −1 к лимиту.
- Void ≠ возврат денег.
- Повтор `external_ref` + клуб — без дубля.
- Импорт и стойка → один канон `payment`.
