## 2. Подключение 2-го и 3-го клуба (тарифы ещё Free/Hobby)

Код менять **не обязательно**, если `check:volume` в зоне «норма».

### Чеклист на каждый новый клуб

1. **Supabase:** создать строку в `clubs` (через админку или SQL).
2. **Тренеры:** `users.club_id`, роль `trainer`, `is_active = true`.
3. **Типы абонементов:** завести `membership_types` для клуба.
4. **Планшеты:** вход тренера → Sync → проверить клиентов в Table Editor.
5. **Админ:** выбрать клуб в шапке → клиенты, статистика, продажи (если есть).
6. **RLS:** тренер видит только своих клиентов; админ — выбранный клуб (см. checklist).
7. После недели работы: снова `npm run check:volume`, строка в GROWTH_PLAYBOOK.

### Что может понадобиться в коде (по факту нагрузки)

| Задача | Когда | Приоритет |
|--------|-------|-----------|
| Окно pull тренера (6–12 мес, настройка) | Pull >30–60 с на Wi‑Fi | P1 |
| SQL RPC / view для `club-stats` | `club-stats` >10 с или >50k тренировок | P1 |
| Пагинация тяжёлых справочников | Каталог упражнений >5k на клуб | P2 |
| Изоляция кэша IDB при смене клуба у тренера | Тренер переехал между клубами | P2 |
| Отдельный supervisor / второй админ на клуб | Продуктовое ТЗ [CLUB_SUPERVISOR.md](./CLUB_SUPERVISOR.md) | отдельная фича |

**Не делать:** новые файлы `api/*.js` — лимит **12/12** на Hobby. Расширять `admin-data?action=`.

## 3. Первый коммерческий клуб → Vercel Pro

**Триггер:** клуб платит за сервис (не «личный проект» по ToS Vercel).

### День перехода

1. Апгрейд проекта на [vercel.com](https://vercel.com) → Pro (~$20/мес).
2. Проверить env: `VITE_SUPABASE_*`, `SUPABASE_SERVICE_ROLE_KEY` без изменений.
3. `git push` + `npx vercel --prod --yes` (как обычно).
4. `npm run qa` и `npm run qa:roles` на prod.
5. Запись в GROWTH_PLAYBOOK: Vercel = Pro.

### Что открывает Pro (но не обязательно кодить сразу)

- Запас по serverless (если понадобится вынести тяжёлый handler из монолита).
- Длиннее таймауты для `push-records` при очереди >200 записей.
- Preview/команда для QA второго разработчика.

Подробнее: [PAID_TIER_MIGRATION.md](./PAID_TIER_MIGRATION.md).

## 4. Рост данных → Supabase Pro + фаза 4 в коде

**Триггеры (любой из):**

- БД **>400–500 MB** или рост **>50 MB/мес**
- **5–10+ клубов** в одном проекте
- Стабильные `ERR_CONNECTION_RESET` / таймауты в часы пик
- В договоре нужны **ежедневные бэкапы**

### День перехода Supabase

1. Pro на **тот же** project ref (не новый проект без миграции).
2. Включить бэкапы; описать восстановление для клуба.
3. Повторить [SUPABASE_PROD_CHECKLIST.md](./SUPABASE_PROD_CHECKLIST.md).
4. `npm run qa` после переключения.

## 9. Запланировано: месячные отчёты продаж (материализованная агрегация)

**Статус:** 📋 **согласовано, реализация позже** (2026-07-11). При 1 клубе не срочно; делаем при росте сравнений месяцев, ИСКРЫ и истории.

### Проблема сейчас

| Слой | Как работает |
|------|----------------|
| День | `club_sales_daily` — одна строка на клуб × дату |
| Итог месяца | Считается **на лету** из всех дней (`aggregateMonthFromDailyRows` в `salesReportCore.js`) |
| Сравнение месяцев / ИСКРА MoM | Для прошлого месяца снова тянутся **все daily** (до 31 строк) + тяжёлая статистика зала за период |
| Навигация «пред. месяц» в продажах | `querySalesMonthRows` — полный набор дневных строк |

При одном клубе это терпимо. При годовой истории, частых сравнениях и нескольких клубах — лишний egress и время ответа API.

### Идея (целевая модель)

**Текущий месяц** — по-прежнему `club_sales_daily` (редактирование отчёта за день, графики по дням).

**Закрытые и прошлые месяцы** — одна строка **месячного отчёта** на клуб; при сравнении и аналитике подгружаем **только отчёт**, не все дни.

```
club_sales_daily    → текущий месяц, правки по дням
club_sales_monthly  → итог месяца (1 строка на club_id × year × month)
```

### Что хранить в месячном отчёте (будет расширяться)

Состав метрик **не финальный** — со временем будут добавляться, убираться и меняться поля. Заложить:

- **Ядро в колонках:** прибыль НК/ДК/УК, итого, PNK, тренировки (ручной ввод), дней с отчётом, % плана.
- **Расширяемый блок:** JSON `summary` / `metrics` (матрица 3×3, суммы залов, fit-city агрегаты для ИСКРЫ, payroll-срезы и т.д.).
- **`schema_version`** — чтобы менять формулы без поломки старых месяцев.
- **`updated_at`** — пересчёт при каждом сохранении дня в этом месяце; опционально `closed_at` при «закрытии» месяца.

Правило: **источник правды для дней** остаётся `club_sales_daily`; monthly — **материализованный снимок**, пересчитываемый из daily (не вводится руками отдельно).

### Этапы реализации (когда дойдём)

| Этап | Задача | Результат |
|------|--------|-----------|
| **A** | Миграция `club_sales_monthly` + пересчёт при `saveClubSalesDaily` | В БД всегда актуальный итог месяца |
| **A** | Backfill SQL из существующих `club_sales_daily` | История с прошлых месяцев |
| **A** | `verify-sales-monthly-parity.mjs` ↔ `aggregateMonthFromDailyRows` | Цифры не расходятся с текущей логикой |
| **B** | Статистика продаж / переключение месяцев читает monthly для **прошлых** месяцев | Меньше данных в UI и API |
| **B** | ИСКРА «сравнение с прошлым месяцем» — previous из monthly, не full daily pull | Быстрее prefetch и ответ |
| **C** | Опционально: компактный ряд по дням в monthly (прибыль по датам) для графиков прошлых месяцев | Без 31 отдельных SELECT |
| **C** | Опционально: «закрытие месяца» (после 1-го числа прошлый только из monthly) | Стабильная история |

**Не в первой итерации:** ломать форму дневного отчёта; убирать `club_sales_daily`; отдельный Vercel endpoint (расширять `admin-data?action=`).

### Триггеры «пора делать»

- Жалобы на медленную **Статистику / Аналитику** продаж при листании месяцев.
- ИСКРА MoM стабильно >10–15 с или таймауты на prefetch.
- **2+ клуба** и регулярный просмотр истории >6 месяцев.
- Egress Supabase стабильно >3–4 GB/мес из-за продаж.

### Связь с уже существующим кодом

Переиспользовать, не дублировать правила:

- `aggregateMonthFromDailyRows`, `buildSalesManagerMonthStats`, `buildClubMonthAnalytics` — эталон расчёта до появления таблицы.
- `monthSummary` в bundle продаж — уже тот же смысл, но только в памяти после load.
