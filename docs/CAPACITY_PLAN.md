**Актуально:** 2026-10-08  
**Статус:** 📋 план; этапы запускаются по сигналам ниже, не все сразу.  
**Место в очереди:** [PATH_TO_GOAL.md](./PATH_TO_GOAL.md) §4, ставка **1c**.

## Цель владельца (2026-10-08)

| Показатель | Цель | Сейчас (07.10) |
|---|---|---|
| Тренеров активных | ~300 | ~33 |
| Клиентов в базе | 50–60 тыс. | ~1,6 тыс. |

Запас закладываем ×3 от цели (≈1000 тренеров), чтобы рост клубов не упирался в сервер.

## Где мы сейчас (оценка по коду, без нагрузочного теста)

- Одна ВМ Yandex: 2 vCPU / 4 ГБ, один процесс Node (`os-hybrid`) за Caddy; на ней же сборка при деплое.
- Пул к Managed PG: **8 соединений** (`api/_lib/pgRest/pool.js`, `max: 8`), ожидание соединения 8 с, запрос до 20 с.
- Оценка потолка без изменений: **150–300 тренеров, 5–10 тыс. активных клиентов**. Цель владельца — на верхней границе.
- База 60 тыс. клиентов и ~0,5 млн тренировок в год — нормальный объём для Postgres при индексах; диск 20 ГБ — на годы.

## Риски по порядку

1. **Пик одновременных полных pull** (утро, после деплоя): тяжёлые запросы занимают все 8 соединений → остальные ждут > 8 с → ошибки Sync у тренеров.
2. **Админ-экраны по всей сети**: списки и отчёты, которые читают всю базу клиентов, станут в 30–40 раз тяжелее и отнимут пул у тренеров.
3. **Рассылка напоминаний** (`api/_lib/clientPortal/clientReminderJob.js`): подписки и клиенты читаются одним списком, отправка по одной. На 10 тыс. — длинный `IN (...)` и ~15–20 мин отправки; укладывается в окно 19:00–22:00, но в те же часы, что и вечерний зал.
4. **Деплой на той же ВМ**: сборка съедает CPU на 1–2 мин.
5. **Второй процесс Node** сломает лимиты в памяти: `api/_lib/authRateLimitCore.js` и `api/_lib/moiZvonkiCore.js` держат счётчики в `Map` — на двух процессах лимит входа станет вдвое мягче. До масштабирования процессов счётчики — в PG.

## Этапы

| Этап | Что делаем | Когда запускать | Объём |
|---|---|---|---|
| **A. Дешёвая гигиена** | Аудит admin API и экранов на «грузит всю базу клиентов» → пагинация / агрегат на сервере. Рассылка — пачками (по 500 id, отправка с ограниченной параллельностью). Пул — из env (`PG_POOL_MAX`, по умолчанию 8). | Сейчас, в свободный слот; не ломает зал | 0,5–1 день |
| **B. Нагрузочный тест** | Скрипт только на чтение: N тренеров (полный `trainer-pull`) + M клиентов (`/me`), ступени 10→50→100→200→400. Итог — цифра в этот файл. Нужна отдельная тестовая ВМ (прежний стенд стал продом) или ночное окно на проде. | До волны подключения клубов, когда тренеров ~80–100 | 1–1,5 часа + ВМ |
| **C. Усиление сервера** | ВМ 4 vCPU / 8 ГБ; PG на класс выше; `PG_POOL_MAX=20`; лимиты входа в PG; 2 процесса Node. | Тренеров 100–150 **или** сигнал из таблицы ниже | ~2 часа, перезапуск ночью |
| **D. Сборка вне прода** | Деплой собирает бандл не на прод-ВМ (CI или отдельная ВМ), на проде — только выкладка. Заодно возвращаем стенд для тестов. | Вместе с C или при жалобах «тормозит во время деплоя» | 0,5 дня |
| **E. Горизонталь** | 2+ ВМ за балансировщиком, реплика PG для отчётов и ИСКРЫ. | > 500 тренеров или C упёрся по метрикам | отдельная задача |

Порядок не меняет правил стабильности: офлайн-очередь и контракт `trainer-pull` / `push-records` не трогаем; оптимизации pull — по порядку из `fitness-diary-stability.mdc` (окно pull → индексы IDB → пагинация UI).

## Сигналы (что смотреть)

| Метрика | Где | Порог → этап |
|---|---|---|
| p95 `trainer-pull`, `admin-data` | `api-timing` в журнале сервиса ([DATA_VOLUME.md](./DATA_VOLUME.md) — команда отчёта) | p95 > 3 с в пик → C |
| Ошибки Sync у тренеров (таймаут, 5xx) | жалобы, `docs/INCIDENTS.md` код C | повтор в пик → C |
| CPU ВМ в вечерний пик | Yandex Monitoring | > 60% стабильно → C |
| Соединения PG | Managed PG → мониторинг | у потолка пула в пик → C |
| Активных тренеров | `npm run check:volume`, [GROWTH_PLAYBOOK.md](./GROWTH_PLAYBOOK.md) журнал | 80–100 → B; 100–150 → C |
| Клиентов с приложением | `client_push_subscriptions` / сессии | > 3 тыс. → проверить A (рассылка) сделана |

Метрики раз в месяц записываем в журнал [GROWTH_PLAYBOOK.md](./GROWTH_PLAYBOOK.md).
