# Персональные данные (152‑ФЗ) — какие документы нужны

**Актуально:** 17.10.2026. **Не юридическая консультация** — ориентир, чтобы не наделать ошибок своими силами. Перед первым платным чужим клубом или при вопросе от проверки — один раз к юристу по 152‑ФЗ с этим файлом.

**Ситуация сейчас:** официальных продаж нет; Ядром бесплатно пользуются клубы друзей‑ИП. Бесплатность **не отменяет** 152‑ФЗ: в программе лежат ФИО, телефоны, абонементы, тренировки и переписка клиентов — это персональные данные в любом случае.

Связано: договор — [FRIEND_CLUB_AGREEMENT.md](./FRIEND_CLUB_AGREEMENT.md), текст другу — [FRIEND_CLUB_NOTE.md](./FRIEND_CLUB_NOTE.md), техническая защита — [PROD_SECURITY_CHECKLIST.md](./PROD_SECURITY_CHECKLIST.md), очередь — [PATH_TO_GOAL.md](./PATH_TO_GOAL.md) #3b.

## 4. Если утечка или подозрение на взлом

Закон (ч. 3.1 ст. 21): **оператор** сообщает в РКН в течение **24 часов** о факте и через **72 часа** — результаты расследования. Обработчик обязан сразу сообщить оператору.

1. Закрыть дыру (сменить ключи / пароли, отозвать сессии) — [RUNBOOK.md](./RUNBOOK.md), [INCIDENTS.md](./INCIDENTS.md).
2. **В течение нескольких часов** написать каждому затронутому клубу: что случилось, чьи данные, когда, что уже сделано.
3. Клуб подаёт уведомление в РКН (24 ч) — помочь фактами.
4. Через 72 ч — итог разбора клубу (что утекло, причина, что изменено).
5. Запись INC в [INCIDENTS.md](./INCIDENTS.md) (контур `инфра`, код Q).

## 5. Политика конфиденциальности Ядра (A2)

**В репо, на прод после выкатки:** `/privacy`. Ссылки «Политика конфиденциальности» и «Правила переписки» (`/chat-rules`) — на входе (`/login`, `/coach`, `/me` без сессии) **и** в «Мой профиль» (клиент почти всегда уже внутри `/me` по ссылке клуба; сотрудник редко выходит). Код: `privacyPolicyCore.js`, `chatRulesCore.js`, `LegalEntryLinks`, проверки `verify-privacy-policy.mjs` / `verify-chat-rules.mjs`.

**Содержание (канон для правок текста):**

1. Кто мы: ИП — **обработчик** по поручению клуба (не оператор данных клиентов); реквизиты — публичная оферта `/offer` и договор с клубом; контакт — через клуб; опционально `VITE_PRIVACY_CONTACT`.
2. Чьи данные: клиенты и сотрудники клубов — клуб оператор, мы обрабатываем по его поручению.
3. Какие данные: ФИО, телефон, абонементы, тренировки и замеры, здоровье из карточки, переписка, вход и устройства.
4. Зачем: учёт услуг клуба, связь клиента с тренером и клубом.
5. Где хранятся: серверы Yandex Cloud в РФ; подрядчики — Yandex (хостинг, ИИ‑помощник).
6. Сколько храним: пока клуб пользуется Ядром; после ухода клуба — удаление в течение 30 дней.
7. Как удалить свои данные: обратиться в свой клуб (оператор); мы выполняем по его поручению.
8. Как защищаем: HTTPS, роли, привязка устройств, бэкапы в РФ.

Перед платным чужим клубом — юрист сверяет текст с договором.

## 8. Выкатка оферты: уже работающие клубы

**Что увидит управляющий, который уже давно в системе:** после деплоя при следующем открытии `/club` — экран оферты один раз (короткий лид + текст оферты + галочка). Доступ к данным клуба не стирается; пока не нажмёт «Принимаю и продолжаю», кабинет закрыт этим окном.

| Сценарий | Поведение |
|----------|-----------|
| Управляющий уже вошёл раньше, сессия жива | После обновления приложения / следующего захода — окно один раз |
| Новый управляющий | То же окно при первом входе |
| Тренер / менеджер / админ сети | Окна нет |
| «Он же тренер» (linked) | Оферту принимает только учётка **управляющего**, не тренерская |
| Сменили текст оферты (`OFFER_VERSION`) | Снова один раз у всех, кто принял старую версию |

**Рекомендация:** не проставлять принятие молча — один клик даёт дату и версию в `users.offer_*`. Если принципиально не беспокоить действующих друзей: вручную на ВМ `scripts/sql/grandfather-offer-supervisors.sql` (после миграции колонок) — слабее для спора.

**Порядок на прод:** миграция `20261104120000_users_offer_accepted.sql` → код → (опционально grandfather) → управляющие подтверждают.

## 9. A5 — выгрузка / удаление данных клуба (чеклист)

**Срок:** до **30 дней** с запроса клуба (договор п. 4.2). **Кто просит:** управляющий / ИП клуба в переписке с владельцем (скрин в сейф).

Автокнопки «стереть клуб» в продукте **нет** — слишком легко снести чужой клуб. Делает владелец + агент вручную.

1. **Подтвердить** клуб: название, `club_id` (uuid), что это уход / отзыв поручения, нужна **выгрузка**, **удаление** или оба.
2. **Выгрузка (если просили):** снимок строк клуба (клиенты, абонементы, тренировки, сотрудники без чужих клубов) → зашифрованный архив клубу; пароль — другим каналом. Не класть сырой дамп в общий чат.
3. **Отключить доступ сразу:** пользователи этого `club_id` — неактивны / сессии отозваны; клиентские входы клуба — отозвать.
4. **Удаление живых данных:** только после явного «удаляйте» и после выгрузки (если была). Порядок и таблицы — агент смотрит схему (`docs/DATA_MODEL.md`), удаляет **только** строки с этим `club_id` (и зависимые), на **проде через согласованный SQL на ВМ**, с бэкапом «до». Чужой `club_id` не трогать.
5. **Бэкапы:** в свежих копиях клуб пропадёт после ротации (ориентир — политика бэкапа в [RELIABILITY_PLAN.md](./RELIABILITY_PLAN.md)); отдельно вычищать старые encrypted-копии — только если клуб настаивает и владелец подтвердил.
6. **Ответ клубу:** дата выгрузки/удаления, что доступы закрыты; запись короткой строки в переписку-сейф владельца (не обязательно INC, если не инцидент).

Повторный запрос того же клуба — не плодить вторую процедуру; свериться с сейфом.
