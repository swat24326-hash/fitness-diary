## 2. Владелец — как писать, чтобы дешевле (и не хуже)

1. **Один чат = одна задача.** Новая большая тема → новый чат. Длинная история дороже нового старта с `@AGENTS.md`.
2. **В первом сообщении:** цель + файл/экран/симптом. Пример:  
   `Баг: после Sync на планшете пропадает черновик. Смотри docs/SYNC.md и INCIDENTS код C.`
3. **Не прикреплять весь проект** (`@` на корень). Лучше: `@AGENTS.md` или одна папка `src/lib/sync*`.
4. **Мелочь** (опечатка, цвет кнопки) — короткий запрос без handoff и без «прочитай всё».
5. **Фича / приоритет** — ссылка на один файл (`PATH_TO_GOAL`), не копировать ТЗ целиком в чат.

### Шаблон первого сообщения

```
Задача: <баг | фича | док | деплой>
Где: <экран / файл / роль>
Симптом или цель: <1–2 предложения>
Уже смотрел: <если есть — INC / файл>
Не трогать: <если важно>
```

## 3. Агент — как не жечь токены (без минусов для качества)

| Дорого и лишнее | Дешевле и безопасно |
|-----------------|---------------------|
| Читать все `docs/` подряд | Playbook §3 → 1–2 файла |
| «Разведка» всего репо глазами | `grep` / Glob по имени |
| 3 subagent без нужды | Один узкий поиск, если зона известна |
| Перечитывать одни и те же файлы | Держать выводы; править сразу |
| Длинный ответ «на всякий случай» | Суть → детали по запросу |
| `qa:local` на косметике | `lint` всегда; qa/verify — по ship/stability |

**Не экономим:** правила `.cursor/rules/`, цикл INCIDENTS на жалобе, `qa:critical` / verify на sync / абон / завершение тренировки / agg.

## 4. Правила Cursor

Все политики проекта **действуют**. Но в каждый запрос грузятся не все: 12 правил постоянно (~33 500 символов против ~43 300 в 14 правилах раньше), а два самых больших — **по типу задачи**:

| Правило | Когда подключается | Размер |
|---------|--------------------|--------|
| `fitness-diary-features.mdc` | Новая фича или развитие функции — до плана и кода | ~7 500 символов |
| `fitness-diary-north-star-lead.mdc` | Приоритет, «что дальше», оплаты, переезд РФ | ~2 400 символов |

Так каждый мелкий запрос (опечатка, цвет кнопки) стал дешевле на ~23% постоянного объёма правил, а на фиче политика подключается целиком.

Остальные шестнадцать правил подключаются по `globs` (файлы задачи) — sync, домен, лояльность, ПНК, прайс, ЗП, продажи, клиенты админки, питание и ДЗ, пульс, главная тренера, ежедневник, ИСКРА, Supabase, UI, разбиение файлов. Полный контракт домена живёт в `docs/`, в правиле — только инварианты: так правило дешевле и не расходится с каноном (лояльность: 3 600 символов правила против 25 300 в [LOYALTY.md](./LOYALTY.md)). Узкая зона получает своё правило вместо раздела в общем: вёрстка доски ПНК больше не грузится при правке формы тренировки.

`node scripts/verify-rules.mjs` держит эти цифры честными: проверяет, что ссылки правил ведут на существующие файлы, `globs` реально что-то матчат, постоянная часть не выросла выше бюджета, а на одном файле не собирается лавина правил (входит в `qa:local`).

Сколько правил приходит на один файл: чаще всего одно-два, максимум три — например компонент доски ПНК берёт ПНК + разбиение файлов + UI, это ~47 400 символов против 35 600 постоянных. Скрипт следит, чтобы этот худший случай не рос.

**Чтобы качество не просело**, жёсткие рамки остались в постоянной части `fitness-diary-architecture.mdc`: цель продукта, «оплаты и касса только после R3+», «не стартовать переезд без явной команды» и таблица «какое правило открыть на какой задаче». Триггеры продублированы в [`AGENTS.md`](../AGENTS.md).

Список правил: [PROJECT_HANDOFF_FOR_AI.md](./PROJECT_HANDOFF_FOR_AI.md) §15, playbook §4. Хуки: [HOOKS.md](./HOOKS.md).

## 5. Когда карта «устарела»

Если сменились роли, API, sync или критический путь — обновить handoff / API / SYNC / CODE_TRACE **в той же задаче** (`fitness-diary-docs.mdc`). Новый файл в `docs/` → строка в [README.md](./README.md).
