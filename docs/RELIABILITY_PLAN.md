## Зачем

Решение владельца (2026-10-09): **касса подключается последней**. До неё приложение должно работать без сбоев, а при сбое мы узнаём о нём раньше тренеров и умеем вернуть данные.

Аудит 09.10 нашёл три дыры, не видимые в зале, пока не случилась беда:

1. **Падение прода никто не замечает** — закрыто 2a (кроме «ВМ лежит целиком» → 2b).
2. **Копии базы только на той же ВМ и в том же кластере** — автокопии Managed PG (7 дн.) и ночной `pg_dump` на диске ВМ. Защита кластера от удаления ✅ с 07.10 (GrokBot `2026-10-07-02`). Пробного восстановления не было.
3. **Нет тестового стенда** — прежний стенд стал продом; каждая выкатка сразу в зал, сборка грузит боевую ВМ.

**Решение владельца (2026-10-09):** 2b — сейчас внутри Yandex Cloud; **2d — самая последняя задача, сразу после кассы** (PATH_TO_GOAL §4, ставка 11). Пока 2d нет, остаётся риск: при блокировке аккаунта Yandex недоступны все копии разом.

**Как устроено 2a.** `scripts/ops-alerts-vm.mjs` (cron на ВМ, `scripts/ops-alerts-install-vm.sh`) проверяет раз в минуту приложение, сайт через `PUBLIC_ORIGIN`, базу (`SELECT 1`) и диск; логика — `api/_lib/opsAlert/` + `verify-ops-alerts.mjs`. Сообщения — от закрытого сообщества ВК (`VK_ALERT_TOKEN`, `VK_ALERT_PEER_IDS`; записать — `scripts/ops-set-vk-alert-key.ps1`). Что делать по сообщению — [RUNBOOK.md](./RUNBOOK.md) §9. **Предел:** сторож живёт на той же ВМ — если ВМ лежит целиком, он молчит; закрываем в 2b(3).

**Как устроено 2b(1–2).** `scripts/pg-backup-vm.sh` после локальной копии зовёт `scripts/pg-backup-upload-vm.sh`: шифрование `gpg` (AES-256, пароль `/etc/fitness-diary/backup.pass`, копия пароля — у владельца вне ВМ) → `PUT` в бакет `PG_BACKUP_BUCKET` с токеном сервисного аккаунта ВМ (без статических ключей; права только «загрузка + чтение» на этот бакет — удалить копию с ВМ нельзя). `scripts/pg-restore-drill-vm.sh` (cron 1-го числа) — скачать, расшифровать, поднять во временном Postgres, сверить строки. Обе строки — в утренней сводке. Установка — `scripts/pg-backup-cloud-setup-vm.sh <бакет>`.

**Как устроено 2b(3).** `ops/uptime-function/index.mjs` → `node scripts/build-uptime-function.mjs` → один файл `ops/uptime-function/dist/index.js` для редактора Yandex Cloud Functions (функция `app-core-uptime`, таймер раз в минуту, сервисный аккаунт `uptime-fn`). Логика тревог та же, что у сторожа (`watchdogState.js`), состояние — `uptime-state.json` в бакете `app-core-uptime-state`, ключ ВК — секрет Lockbox `vk-alert`. Сообщения с пометкой «проверка снаружи». Сценарий целиком — в `verify-ops-alerts.mjs`. После правки логики — пересобрать и обновить код функции в консоли (задача GrokBot). Ключ ВК в функции привязан к конкретной версии секрета: при смене ключа сообщества — новая версия секрета и новая версия функции, иначе внешняя проверка будет слать со старым ключом.

**Как устроено 2c.** ВМ `app-core-stand` (Ice Lake 2 vCPU 50 % / 4 ГБ / HDD 20 ГБ, та же подсеть) **выключена**, пока нет выкатки: платим только за диск (HDD дешевле SSD) + минуты работы. Вход — только SSH с прода (группа `stand-sg`). На стенде свой PostgreSQL 16 с тестовым клубом (`c2-seed-staging.mjs`), свой `JWT_SECRET`; секретов прода нет, с прода — только публичные `VITE_*`. Выкатка `sudo bash scripts/deploy-vm.sh origin/main` на проде: `stand-ctl-vm.sh start` (Compute API токеном сервисного аккаунта ВМ) → на стенде `stand-check-vm.sh` (миграции на базу стенда, сборка, `stand-smoke.mjs`: вход тренера/админа, pull, запись завершённой тренировки, 401/403) → проверенный `dist` копируется на прод, `r3-deploy-vm.sh` с `PREBUILT_DIST` (тот же коммит, прод не собирает) → стенд выключается. Упал стенд — прод не тронут. Аварийно без стенда — старый `r3-deploy-vm.sh`. Подключение стенда: `stand-install-vm.sh <instance-id> <IP>`. **Сразу после подключения стенда** — следующие задачи на нём: смена apt-источника Caddy (402), нагрузочный тест (этап B) и задача A2 «Клиенты без полной перекачки» из [CAPACITY_PLAN.md](./CAPACITY_PLAN.md) (решение владельца 09.10).

Порядок не случаен: 2a дешевле всех и сразу сокращает время простоя; 2b защищает от необратимого; 2c снижает риск новых регрессий.
