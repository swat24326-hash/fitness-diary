## Причина архива ✅

**Зачем:** знать, почему человек не в операционке (отток / переезд / не продлил…).

| Поле | Смысл |
|------|--------|
| `clients.archive_reason` | Текст до 200 символов |
| `clients.archive_reason_at` | Когда указали / обновили |
| `clients.expected_return_on` | Дата-ориентир при «Вернётся позже»; очищается при «Вернуть» |

**UI:** модалка с чипами причин (`ClientArchiveReasonModal`) + «Другое» со своим текстом; для **«Вернётся позже»** — обязательный горизонт (1 / 2 / 3 мес. / полгода / своя дата). В списке Архив — факт «Причина» + подсказка «Ждём до…» / «Срок прошёл»; на карточке — баннер.

**Чипы (2026-08):** Не вернётся · Вернётся позже · Не ходит / пропал · Дорого / нет денег · Здоровье · Переехал / другой зал · К другому тренеру · Перешёл в ТЗ · Перешёл в АЗ · Недоволен · Другое. «Перешёл в ТЗ/АЗ» — клиент остался в клубе, но ушёл с ПЗ на абон ТЗ или АЗ (не отток из клуба). Старый чип «Закончил / не продлил» в UI убран; уже сохранённые записи группируются в статистике как legacy.

**Правила:** `src/lib/clientArchiveReasonCore.js` · `clientArchiveExpectedReturnCore.js` · sync: `clientArchiveSyncService.js` · verify: `node scripts/verify-client-archive-reason.mjs`, `node scripts/verify-client-archive-expected-return.mjs`.

**Критично:** любой возврат в работу (кнопка «Вернуть», связка оплат / lite / desk) чистит `archived_at`, причину и `expected_return_on`. Иначе живой клиент остаётся с «хвостом» причины.

**Баллы ПЗ:** в модалке «В архив» — предупреждение, сколько сгорит. «Вернуть» **не** восстанавливает копилку. Канон: [LOYALTY.md](./LOYALTY.md).

**Миграция на прод:**

```bash
npm run db:migrate:clients-archive-reason -- --linked
npm run db:migrate:clients-expected-return -- --linked
```

## Статистика и «Не активные» (рекомендация)

**Воронка в Клиентах / дашборд дня** (чип «Не активные»):

- Финал пути абона: после «Давно не был» (>60 дн.) или странный/пустой абон; без пересечения с «Закончился» / «Давно».
- Только `archived_at IS NULL`; открытый ПНК — в чипе «ПНК», не здесь.

**Статистика периода** (карточка «не активные» за месяц в отчёте):

- Широкий census «нет абона для тренировки на дату периода» (`hasUsableMembershipForPeriodStats`) — **не** то же правило, что финал воронки.

**История за прошлые периоды** (завершённые тренировки в мае 2024, годовой график, журнал за месяц):

- Считаются **факты в том периоде** (тренировки, абонементы), даже если клиент позже ушёл в архив.
- Иначе цифры за прошлые месяцы «поплывут» после архивации.

**Итог:** архив = не в ежедневной работе; прошлая статистика клуба не пересчитывается задним числом. Воронка клиентов ≠ census статистики периода.

## Фаза B — ручной архив ✅ (код + миграция в репо)

1. Миграция: `clients.archived_at TIMESTAMPTZ NULL`, индекс `(club_id, archived_at)` — `20260602120000_clients_archive.sql`.
2. Sync: поле в push/pull (`clients` уже в очереди).
3. `loadTrainerWorkspaceSnapshot`: по умолчанию без архивных; отдельный pull для вкладки «Архив».
4. UI тренера и админа: вкладки **Активные** | **Архив**; «В архив» / «Вернуть»; read-only карточка в архиве.
5. Агрегация «Не активные»: `filterOperationalClients` в `clubStatsAgg` / `clubClientPeriodAgg`.

**Перед prod:** в Supabase SQL Editor выполнить миграцию (если ещё не применялась):

```sql
-- из supabase/migrations/20260602120000_clients_archive.sql
ALTER TABLE public.clients ADD COLUMN IF NOT EXISTS archived_at TIMESTAMPTZ;
CREATE INDEX IF NOT EXISTS idx_clients_club_archived_at ON public.clients (club_id, archived_at);
```
