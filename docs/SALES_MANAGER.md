# Менеджер по продажам + финансы клуба — ТЗ

**Статус:** ✅ **в проде** (роль `sales_manager`, маршруты `/sales`, `/sales/clients`, `/sales/pnk`, `/sales/club-tasks`; админ — `/admin/sales`). Документ ниже — согласованное ТЗ и справочник полей; при расхождении с UI смотреть код (`AdminSales`, `AdminClients`/`SalesClients`, `api/_lib/adminData/salesHandlers.js`).  
**Связано:** воронка ПНК — [PNK_FUNNEL.md](./PNK_FUNNEL.md).  
**Не путать с:** [CLUB_SUPERVISOR.md](./CLUB_SUPERVISOR.md) — управляющий (`supervisor`, ещё не в коде): на своём клубе продажи **как у админа клуба**; не менеджер продаж.

---

## Роли и зоны

| Роль | Клуб | Ежедневный отчёт | Расход (одна сумма) | План / сводки | Прочее |
|------|------|------------------|---------------------|---------------|--------|
| **Менеджер по продажам** | один свой | ✅ заполняет, правит прошлые дни | ❌ **не видит** | сосуд + свой клуб | отчёт + **прайс** + **клиенты клуба** (как у админа: фильтры ДР/воронки, ТЗ/АЗ, lite-ПЗ) |
| **Управляющий** | один свой | 👁 просмотр отчётов | ✅ параметры + расход | свой клуб + **итоги** | **зона финансов** на той же странице |
| **Админ** | переключатель клуба | ✅ ввод + правка | ✅ параметры + расход | все клубы | **обе зоны** |

**Менеджер по продажам:** один на клуб.  
**Ежедневный отчёт:** один на **клуб / день**.

## Модуль 1 — Ежедневный отчёт отдела продаж

### Поля дня

| Поле | Код | Тип | Описание |
|------|-----|-----|----------|
| Дата | `report_date` | date | Календарный день |
| Клуб | `club_id` | uuid | UNIQUE вместе с датой |
| Прибыль **НК** | `profit_nk` | ₽ | Заработок за день по **новым** клиентам |
| Прибыль **ДК** | `profit_dk` | ₽ | По **действующим** |
| Прибыль **УК** | `profit_uk` | ₽ | По **ушедшим** |
| **Итого за день** | `profit_day` | ₽ | **Считает сайт:** `profit_nk + profit_dk + profit_uk` (не вводится отдельно) |
| ПНК | `pnk_total` | шт. | **Одно число** — потенциальные новые клиенты (**без** ПЗ/ТЗ/АЗ) |
| Тренировок проведено | `trainings_count` | шт. | **По всему клубу за день**, вводит **менеджер вручную** |

**Тренировки:** не тянем из планшетов тренеров — не у всех есть устройства. Отдельное поле в отчёте; позже можно **подсказку** из FIT-CITY (readonly), но **источник v1 — ручной ввод менеджера**.

### Когда что загружать

Все Excel из 1С ниже — **переходный мост** к правде в Ядре ([PRODUCT_VISION.md](./PRODUCT_VISION.md)). Конечная цель по деньгам — домен платежей: [PAYMENTS_DOMAIN.md](./PAYMENTS_DOMAIN.md).

| Что | Файл / источник | Кто | Когда | Зачем сейчас | Цель после моста |
|-----|-----------------|-----|-------|--------------|------------------|
| **Отчёт по оплатам** | как `31.xlsx` из 1С | менеджер / админ | **Каждый день** (вечером или утром за вчера) | Подставить день в отчёт (НК/ДК/УК). Ручной ввод можно | Строки **платежей** в Ядре → день = agg; файл — сверка/догонка |
| **Список заканчивающихся** | Excel 1С: карта + ФИО + дата окончания (+ тип ТЗ/АЗ, цена) | **только админ** | **Раз в период** → **Списки из Excel** | Desk без тренера + `desk_hall` → вкладки ТЗ/АЗ | Те же клиенты/абоны ведутся в Ядре; перезалив реже |
| **Заявка тренеру (клип)** | руки из продажи / кассы → Ядро | менеджер | **Днём**, сразу после продажи | Заявка «создай абон»; правда = кнопка на планшете | То же + связь с `payment` |

**Важно:** старые ручные дни отчёта сами **не пересчитываются**. Закрытия **не заменяют** дневной отчёт.

Служебный тренер «Не назначен» для desk **больше не нужен** (легаси-строки на holding по-прежнему вне KPI).

### Заявка тренеру на абон (день)

- UI: плитка / вкладка **«Заявка тренеру»** — `/sales?tab=clips` (менеджер) или `/admin/sales`.
- API: `admin-data?action=sale-clips` (GET список / POST create|cancel|match).
- Тренер после Sync видит awaiting на главной (пустое состояние: «заявок нет» + Sync) и в карточке клиента → **«Создать по заявке»** (`memberships.clip_id`, статус `done`).
- Мягкий чеклист дня: висящие awaiting — без блокировки отчёта.
- Verify: `node scripts/verify-sale-clips.mjs`.

### Импорт Excel «Отчёт по оплатам» (1С) — переход

**Статус моста:** ✅ в проде. **Цель:** строки платежей в Ядре — [PAYMENTS_DOMAIN.md](./PAYMENTS_DOMAIN.md). Сейчас импорт **не** сохраняет ledger: только превью → форма дня → `club_sales_daily`.

На вкладке дневного отчёта (админ и менеджер): загрузка `.xlsx` → превью строк (карта, зал, сумма) → галочки **НК / ДК / УК** → «Подставить в форму дня» → обычное **Сохранить**.

Ниже — блок **«Карточки из оплат»**: KPI (уже в Ядре / ПЗ без карточки + сумма / desk) → приоритетный список **ПЗ без карточки** (тренер обязателен; без планшета → lite, с планшетом → клип; «Создать готовые») → затем ТЗ/АЗ desk. Это уже шаг к CRM в Ядре; следующий — не потерять сами суммы как `payment`.

- Парсер (адаптер 1С): `src/lib/admin/salesPaymentsImportCore.js`
- Связка карточек: `salesPaymentsLinkCore.js` + `SalesPaymentsClientLinkSection.jsx`
- ТЗ/АЗ без абона в Ядре — сегмент **не** ставится автоматом (чтобы не было ложного НК)
- Клубная карта → «Доп. продажи»
- Касса / DDS / УК1 — **не в импорте оплат** (см. PAYMENTS_DOMAIN + PRODUCT_VISION)
- Verify: `node scripts/verify-sales-payments-import.mjs`, `node scripts/verify-sales-payments-link.mjs`

**Старые отчёты:** дни, уже заполненные вручную по прежней методике, **не пересчитываем** автоматически. Импорт — для новых дней (или явная ручная подстановка в выбранную дату). Сравнение месяца «до/после» старта импорта может дать ступеньку в цифрах — это ожидаемо.

### Импорт Excel часов ПЗ (`otchet_pz.xlsx`) — переход

**Статус моста:** ✅ в проде. На дневном отчёте (админ и менеджер) — **две квадратные карточки в ряд**: оплаты `31.xlsx` | часы ПЗ `otchet_pz.xlsx`.

Файл — матрица **тренер × тип карты** за день (не посессии по клиентам). Превью: **итог файла N → в Ядро попадёт M** (частичное совпадение ФИО/типов). «Подставить» → матрица «Тренировки по типам карт» → «Сохранить».

**Контракт дня (без double-count):**
- **Old day** — только строки `__club__` (ручной ввод «По клубу»).
- **New day** — только реальные `trainer_id`; строка «По клубу» в UI = **сумма тренеров** (read-only).
- В одном дне **нельзя** смешивать `__club__` и тренеров.

**Два мира до CRM:** эта матрица — **отчёт менеджера из 1С**, не статистика планшетов и не ЗП из дневника тренера. Цифры могут расходиться, пока нет полной стыковки.

- Core: `pzTrainingsReportImportCore.js` / `pzTrainingsReportImportWorkbook.js` / `salesTrainingsMatrix.js` (`resolveTrainingsMatrixForPersist`, `hydrateTrainingsMatrixInputMap`)
- UI: `SalesDailyPzTrainingsImportSection.jsx`, `SalesTrainingsMatrix.jsx`
- Verify: `node scripts/verify-pz-trainings-report-import.mjs`

### Список заканчивающихся (админ → Списки из Excel)

Вкладка **`/admin/excel-lists`**: **«Список заканчивающихся (ТЗ и АЗ)»** (зал из файла). Часы ПЗ и дневные оплаты — **не сюда**, а в отчёт продаж (`otchet_pz.xlsx` / `31.xlsx`).

Один Excel из 1С: карта + ФИО + дата окончания (+ **цена**, **тип карты**, срок вроде «6 мес»). Зал берём из «Абонемент.Тип карты» (`ТЗ` / `ТЗ Утро` → `tz`, `АЗ` → `az`). Строки без ТЗ/АЗ не создаём. **Одна карта = одна строка** (несколько листов схлопываются по номеру карты, берём более поздний конец). Срок «N мес» задаёт `start_date` пакета; без срока — 1 месяц. Клиенты → **`trainer_id = null`** + `desk_hall` + membership с датами и `paid_amount`. Живые абоны не затираются. CHECK в БД: null-тренер только при `desk_hall` tz|az.

- UI: **Админ → Списки из Excel**. Результат: **Клиенты** → вкладки **ТЗ** / **АЗ**; с живым тренером — вкладка **ПЗ**.
- После сида: `desk_hall` = tz|az, без тренера; карточка **упрощённая** + блок **«Абонементы»**. KPI / «неактивные» desk не считают.
- **АЗ — направление:** на вкладке АЗ колонка «Направление» (Бокс, Техника дня…); на карточке абона — направление, **сроки** и **кол-во занятий** (без пакета «N месяцев»; пакет месяцев — только ТЗ). Типы АЗ: `Структура → Типы абон.` → АЗ → `membership_type_id`.
- **АЗ — списание занятий:** на вкладке АЗ и в карточке — «Списать занятие» (если нельзя — понятная причина); в абонементе — «Журнал» (даты). В визит пишется направление на момент списания. В дневном отчёте: пустые ячейки матрицы АЗ подставляются из списаний при открытии дня; если цифры ещё меньше списаний — баннер и «Довести матрицу». Ручные числа вниз не затираем. Миграция: `npm run db:migrate:memberships-session-visits -- --linked`.
- Старые без зала: выбрать ТЗ/АЗ на карточке **или** снова загрузить Excel → действие «зал» (и `trainer_id` обнулится).
- Миграции: `npm run db:migrate:desk-hall -- --linked`, затем `npm run db:migrate:desk-null-trainer -- --linked`.
- Core: `deskClosingImportCore.js` / `deskClosingApplyService.js` / `holdingClientsCore.js` / `deskHallClientsCore.js` / `deskAzSessionDeductCore.js`
- Verify: `verify-desk-closing-import.mjs`, `verify-desk-hall-clients.mjs`, `verify-desk-az-session-deduct.mjs`, `verify-sale-clips.mjs` (operational filter)

## Одна страница — две зоны (видимость по роли)

**URL:** `/admin/sales?club=<id>` — **один экран** для всех ролей.  
Состав блоков **зависит от роли**: менеджер видит **только зону A**; админ и управляющий — **A + B**.

### Зона A — «Отчёт продаж» (менеджер + админ + управляющий)

Менеджер **заполняет и сохраняет**. Управляющий (когда роль будет) — **как админ этого клуба** (ввод/правка в своём `club_id`). Админ сети — ввод/правка + выбор клуба.

```
┌──────────────────────────────────────────────────────────┐
│  A1. ПЛАН МЕСЯЦА — «сосуд» (анимация)                   │
│      Факт Σ profit_day / plan_total                      │
│      План редактирует только админ (кнопка в зоне B)     │
├──────────────────────────────────────────────────────────┤
│  A2. Дата: [ … ]   ◀ ▶                                   │
├──────────────────────────────────────────────────────────┤
│  A3. Прибыль за день (₽):  НК  ДК  УК  → Итого (авто)    │
│  A4. ПНК (шт)                                            │
│  A5. Тренировок за день, клуб (шт) — вручную            │
│  A6. Матрица ПЗ/ТЗ/АЗ × НК/ДК/УК (шт)                    │
│  [ Сохранить отчёт ]  — только менеджер / админ          │
└──────────────────────────────────────────────────────────┘
```

### Зона B — «Финансы управляющего» (**менеджер не видит**)

Только **админ** (v1) и **управляющий** (позже). Блок **не рендерится** и **не отдаётся API** роли `sales_manager`.

```
┌──────────────────────────────────────────────────────────┐
│  B1. План на месяц (редактирование)                       │
│      plan_total, plan_pz, plan_tz, plan_az               │
├──────────────────────────────────────────────────────────┤
│  B2. Параметры управляющего за месяц                     │
│      Аренда · Расходы · Оклады · Бухгалтерия · Отдел продаж │
│      Итого = сумма статей → amount                       │
├──────────────────────────────────────────────────────────┤
│  B3. Итоги (считает сайт, только чтение)                 │
│      • Заработок месяца     = Σ profit_day               │
│      • Расход               = amount (итог статей)       │
│      • Чистая прибыль       = заработок − расход         │
│      • Σ profit_nk / dk / uk за месяц (опционально)      │
│      • Σ trainings_count за месяц (опционально)          │
│  [ Сохранить финансы / план ]                            │
└──────────────────────────────────────────────────────────┘
```

| Кто | Зона A | Зона B |
|-----|--------|--------|
| Менеджер по продажам | ✅ редактирует отчёт | ❌ **нет доступа** |
| Управляющий | 👁 просмотр | ✅ ввод расхода + **итоговые цифры** |
| Админ | ✅ всё | ✅ всё + выбор клуба |

**Важно:** это **одна страница**, не два URL. У менеджера нижняя часть (B) **отсутствует** — не «скрыта серым», а **не показывается**.

### Прайс персонального зала (менеджер)

Вкладка **Прайс** на `/sales?tab=price` — переключатель **ПЗ | ТЗ**. ПЗ: сетка карт, Excel, Save, печать/PNG. ТЗ: пакеты 1 мес + акции, Excel, Save (печать ТЗ — позже). Чужой клуб недоступен. Docs: [PRICE_LIST.md](./PRICE_LIST.md).

### Клиенты клуба (менеджер)

- UI: `/sales/clients` (плитка **Клиенты** на главной `/sales`, группа «День в зале») — тот же экран, что `/admin/clients`: вкладки ПЗ/ТЗ/АЗ/архив, фильтры сводки без ПНК на ТЗ/АЗ. На **АЗ** — доп. фильтр **по направлениям** (типы абон. АЗ). В **Архиве** — подвкладки **Все / ПЗ / ТЗ / АЗ** (`archiveHall` в URL). **ПЗ и АЗ** — абон жив при сроке *и* остатке занятий; **ТЗ** — только срок. Две кнопки связи: **Max** (чат) и **SMS** (Мои Звонки с телефона клуба), lite-ПЗ, архив, смена тренера. Шапка — cyan shell, «назад» на `/sales`.
- Карточка ↔ список: вкладка, фильтр зала архива, страница и поиск хранятся в query URL — «назад» / крошки возвращают в тот же список.
- Карточка из **Стратегии** (закрытия ДК): `from=strategy` — «назад» снова на Стратегию, не в Клиенты. То же для ПНК/заявок (`from=pnk|clips`).
- Главная менеджера: плитки **двумя рядами** — «День в зале» (Клиенты · ПНК · Заявка · Планёрка) и «Отчёты и рост» (Отчёт · Статистика · Аналитика · Стратегия · Прайс); у каждой короткая подпись.
- Карточка: `/sales/clients/:id` — desk / lite / полный просмотр; тренировки не стартует. Открытие local-first + лёгкий `get-client?scope=glance` для desk ТЗ/АЗ и lite-ПЗ. Список **keep-alive**: при карточке не размонтируется (скрыт) — «назад» без мигания; плюс memory/IDB кэш.
- API: `list-clients`, `list-memberships`, `get-client`, `search`, `clients-last-trainings`, `list-trainers` (свой клуб); push `clients` + `memberships` только своего клуба. Sync менеджера подтягивает клиентов и абоны клуба.
- **Не** отдаём: финансы (зона B), жёсткое удаление ПЗ/lite, чужой клуб. Удаление desk **ТЗ/АЗ** — да (меню «Удалить» на вкладках ТЗ/АЗ); push через `/api/push-record(s)` (роль менеджера допускается, дальше `authorizePush`).
- Verify: `scripts/verify-sales-manager-clients.mjs`.

### Стратегия (менеджер и админ)

Вкладка **Стратегия** (`/sales?tab=strategy`) — **ядро снизу**, не сезонный «якорь»:

1. **Шапка плана:** месяц (текущий / следующий) + **ур. 3** как бюджет пакета. Карточек «база / ожидание × сезон» на экране нет (сезон и сверка отчёта — в свёрнутой справке).
2. **План с Стратегии (модель):** потолок = **ур. 3**; **доп.** = 70% `dop_total` прошлого месяца; бюджет залов = **ур. 3 − доп.**; **ДК** по закрытиям (архив вне); добор **НК/УК** — по **доле выручки зала** за прошлый месяц (внутри зала НК/УК по их ₽); штуки = сумма÷чек; допуск **+15 000 ₽**; **доска**; «В план» без затирания ур. 3.
3. **Playbook месяца** (после «Посчитать»): недели W1…, закрытия ДК — **только кому ещё нужно продление**. Уже купившие следующий абон **не в списке** (число — «Уже купили след.»). В строке — цена абона/покупки (не ×% продления). Снимок: sessionStorage + strategy_snapshot (**update**, не partial upsert — иначе затирались уровни/матрица). Прогресс — Σ profit_day. **Бургер** у чипов недель — полные списки закрытий ПЗ / ТЗ / АЗ за месяц (дата, зал, ориентир ₽, контакты, карточка).
   - ⏸ **После РФ (P1):** из этого списка — кнопка «Назначить» в Планёрку; не отдельная CRM. См. [STRATEGY §5.8](./STRATEGY_SCALE_AND_RU_HOSTING.md).

Verify: `verify-sales-plan-hall-renewals.mjs`, `verify-sales-plan-hall-top-up.mjs`, `verify-sales-strategy-playbook.mjs`, `verify-sales-strategy-playbook-hall-lists.mjs`, `verify-sales-strategy-archive-drift.mjs`, `verify-sales-strategy-snapshot.mjs`, `verify-sales-strategy-package-board.mjs`.

## Визуальный дизайн — **обязательное требование**

Экран продаж — **витрина для менеджера и руководства**, не «серая таблица в Excel». Должен выглядеть **красиво, современно, в духе FIT-CITY** (тёмная тема, зелёный акцент, мягкие карточки — как админ-панель и главная тренера).

### Общий язык

| Принцип | Реализация |
|---------|------------|
| Стиль | Тот же, что `admin-home`, `feature-tile`, `.card` — **не** чужой UI-kit |
| Фон | Тёмный градиент, лёгкое свечение акцента (`--accent-bright`, radial-gradient как у `admin-home__hero`) |
| Типографика | `section-title`, крупные **цифры итогов**, подписи `muted` |
| Отступы | `stagger` / `clamp()` — воздух между блоками, не плотная форма |
| Иконки | Lucide (как в приложении) — календарь, тренд, кошелёк |

### A1 — «Сосуд» с планом (главный визуальный акцент)

- **Центр экрана** в зоне A: стилизованный **сосуд / колба / банка** (SVG или CSS), не просто progress-bar.
- **Жидкость** — градиент зелёный → изумрудный, лёгкий **блик**; уровень = `факт / plan_total`.
- **Анимация:** плавное **заполнение** при открытии страницы (0.8–1.2 s, `ease-out`); после «Сохранить отчёт» — короткий **пульс / подъём уровня**, если изменился факт месяца.
- **Подпись:** «1 240 000 ₽ из 2 000 000 ₽» + **%** крупно; при ≥100% — мягкое «переполнение» (без кричащих цветов).
- **`prefers-reduced-motion`:** без анимации, только статичный уровень.

### A2–A6 — форма дня

- **Переключатель даты** — компактная «pill»-полоска (◀ дата ▶); тап по дате/календарю открывает нативный календарь (выбор любого дня, не только стрелки).
- **Прибыль НК / ДК / УК** — три **карточки-метрики** в ряд (на узком экране — колонка); у каждой подпись категории; **итого** — отдельная выделенная строка с авто-суммой.
- **ПНК и тренировки** — две небольшие карточки рядом (иконка + число).
- **Матрица 3×3** — аккуратная **таблица-сетка**: заголовки ПЗ/ТЗ/АЗ слева, НК/ДК/УК сверху; ячейки — округлые инпуты, hover/focus как у остальных форм.
- **Сохранить** — primary-кнопка; после сохранения — **toast** «Отчёт сохранён» (как в админке).

### Зона B — финансы (только admin / управляющий)

- **Визуально отделена**, но **в том же стиле**: тонкий разделитель или подзаголовок «Финансы клуба» (не другой сайт).
- **B3 Итоги** — **KPI-карточки** (заработок, расход, **чистая прибыль** крупнее остальных); чистая прибыль — главная цифра блока.
- План по направлениям — компактная **горизонтальная группа** полей или мини-таблица с подписями ПЗ / ТЗ / АЗ.
- **Ориентир ПЗ ДК:** кнопки «текущий / следующий месяц» сами открывают нужный месяц плана; % продления (по умолчанию 80%); для текущего вычитается факт шт. ПЗ ДК из дневных отчётов; превью → «В план». См. [PRICE_LIST.md](./PRICE_LIST.md) §P4.
  - **План и прогноз** (`SalesFinanceForecast` + `clubFinanceForecastCore`):
  - **Текущий месяц:** четыре KPI — **План** → **Факт** → **Темп** → **Прогноз** (экстраполяция на конец месяца).
  - **Возвраты** в прогнозе — темп будни/выходные при ≥2 днях с возвратом; иначе факт. ЗП ПЗ/АЗ — от прогноза часов × средняя ставка.
  - **Прошлый месяц:** только факт отчётов (`closed_month_fact`) — «Итоги месяца», без темпа/прогноза; колонка «Прогноз» скрыта.
  - **Будущий месяц:** ни факта, ни прогноза.
  - Отставание по залам — в таблице направлений. Когда блок факта уже в прогнозе/итогах, дублирующие KPI «Итоги месяца» не показываются.
  - Verify: `scripts/verify-club-finance-forecast.mjs`, `scripts/verify-sales-strategy-admin-finance.mjs`.
- **Сравнение плана по сегментам** (`SalesPlanMatrixCompareTable` + `salesPlanMatrixCompare`): статус «В темпе» / «Отстаём» — по **сумме к темпу** и **прогнозу** к концу месяца; под бейджем столбиком — короткие метки **абоны** / **чек** / **прогноз** и цифры отставания. Verify: `scripts/verify-sales-plan-matrix-compare.mjs`.
- Без «сырых» `<table>` без стилей — только оформленные блоки.

## Модуль 3 — Расход управляющего и прибыль

| Решение | |
|---------|---|
| Ввод | **Пять статей** за календарный месяц: Аренда · Расходы · Оклады · Бухгалтерия · Отдел продаж |
| Итого | Считается само (сумма статей); в БД — `amount` + `amount_*` |
| Legacy | Старая одна сумма без статей при открытии попадает в «Расходы» |
| Кто вносит | **Админ** / **управляющий** (финансы / план месяца) |

### Итог по месяцам (сайт считает)

```
Итого заработок месяца  = Σ profit_day  (все дни месяца)
Расход управляющего     = amount (= сумма статей)
Чистая прибыль месяца   = Σ profit_day − amount
```

Миграция колонок: `20260806160000_club_supervisor_expense_parts.sql`, `20260806170000_club_supervisor_expense_sales.sql`. Verify: `scripts/verify-supervisor-expense-parts.mjs`.

Сводки: по месяцам, по клубу; при необходимости — таблица дней + матрица (агрегаты количеств по НК/ДК/УК и ПЗ/ТЗ/АЗ).

**Тренировки в аэробном зале (статистика месяца):** клик по числу (тип или «Итого») открывает окно как у абонемента — список дней с количеством; тап по дню → дневной отчёт. Логика: `buildAerobicTypeDayBreakdown` в `aerobicSalesMatrix.js`.

**Новый тип АЗ (колонка Бокс / R1+ / R3+…):** админ создаёт в «Структура → Типы абон.» (раздел АЗ) и делает Sync. У менеджера — **«Обновить»** на странице отчёта (или Sync в шапке после деплоя фикса). Типы АЗ приходят из облака; без политики `fit_membership_types_sales_manager_read` и доступа к `action=membership-types` менеджер видел только устаревший локальный список.

**Админ:** параметр `?club=` — продажи, план/факт, финансы **выбранного клуба**.
