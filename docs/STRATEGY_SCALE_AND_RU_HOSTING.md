## 0. Ситуация → польза → развитие

### Ситуации

1. **Управляющий в 8:00** открывает админку с телефона / ноутбука клуба: нужны цифры и ИСКРА без «сайт не открылся из‑за зарубежного хостинга».
2. **Тренер в зале** на планшете без стабильного Wi‑Fi: тренировка пишется офлайн; вечером Sync должен уйти в облако, которое доступно из РФ и не «заморожено» паузой Free.
3. **Собственник сети** подписывает договор: «где лежат данные клиентов? можно ли в РФ? кто бэкапит?» — без ответа сделка тормозит.
4. **Разработчик** при 5–10 клубах: лимит 12 functions, egress, медленный pull — нужна ясная очередь работ, а не «перепишем всё».

### Польза

- Продукт остаётся **офлайн-first для зала** и **цифры + действие для кабинета**.
- Инфра растёт **по триггерам**, не «на всякий случай».
- Путь на **российские серверы** понятен заранее: без сюрприза в день договора.

### Вердикт фильтра идеи

| Идея | Вердикт |
|------|---------|
| Дожать масштаб по текущему ROADMAP (клубы, Pro, фаза 4) | **Делаем** — уже в docs |
| Заложить стратегию РФ-хостинга + правило портативности | **Делаем** — этот документ + `.cursor/rules/fitness-diary-hosting-portability.mdc` |
| Учитывать портативность в каждом PR (env, `_lib`, без lock-in) | **Делаем сейчас** — без cutover |
| Сразу переезжать с Vercel/Supabase | **Отложить** — этапы R2–R4 только по явной команде |
| Усиление безопасности (rate limit входа, убрать хардкод админ-email, жёстче роли) | **Отложить** — после переезда на РФ (§5.7); до cutover не стартовать отдельным PR |
| Параллельно строить второй стек «с нуля» | **Не делаем** — дубль и риск sync |

## 1. Как устроены лучшие программы «нашего класса»

FIT-CITY ближе не к «сайту клуба», а к связке:

- **Планшет в зале** (как POS / field app): офлайн-запись, очередь, синхронизация.
- **Кабинет сети** (как HQ SaaS фитнеса: Mindbody / Glofox / Trainerize по духу): роли, отчёты, задания, AI-советник.

| Принцип у лидеров | Что это значит на практике | У нас сейчас |
|-------------------|----------------------------|--------------|
| **Офлайн-first на точке** | Пишем локально; сеть — бонус | ✅ IDB + `sync_queue` + flush→pull |
| **Облако = источник правды** | Конфликт: pending не затираются pull | ✅ `putStoreUnlessPendingSync` |
| **Тонкий UI, толстый домен** | Правила в сервисах, не в JSX | ✅ частично; strangler god-файлов ongoing |
| **Мульти-тенант по клубу** | `club_id`, RLS, изоляция | ✅ клубы + RLS; supervisor ещё ТЗ |
| **Один API-шлюз** | Мало entrypoints, много actions | ✅ `admin-data?action=` (лимит Hobby) |
| **Агрегаты, не «грузи всё»** | Stats/RPC при росте | ✅ Node agg + verify; SQL RPC — фаза 4 |
| **Наблюдаемость** | Логи, алерты, smoke на prod | ✅ weekly smoke; Sentry — по согласованию |
| **Регион данных рядом с клиентом** | Latency + договор + устойчивость | ⏸ сейчас US SaaS (Vercel + Supabase) |
| **Платёжный / юр. контур региона** | Счета, 152‑ФЗ, поддержка | ⏸ продукт готов; инфра — план §5 |
| **Деплой без боли** | Preview, rollback, чеклист | ✅ `qa:local`, RELEASE; домен свой — опционально |

**Вывод:** по архитектуре продукта мы уже на стороне «взрослых» офлайн+SaaS. Главный разрыв с лидерами рынка РФ — **не фичи зала**, а **регион хостинга, договорная зрелость инфра и операционный масштаб 5–10+ клубов**.

## 3. Целевая картина (12–24 месяца)

Один продукт, три опоры:

```
Планшет (офлайн)  →  API + Postgres (регион РФ)  →  Админка / ИСКРА / продажи
```

1. **Зал** — как сейчас: минимум тапов, Sync по кнопке, понятные ошибки на русском.
2. **Сеть** — 5–10 клубов на одном контуре с бэкапами и мониторингом.
3. **Инфра** — данные и API в РФ (или гибрид на переходный период); фронт с CDN в РФ.

Не цель «переписать под микросервисы». Цель — **тот же контракт sync**, другой адрес серверов.

## 5. Трек: переход на российские серверы

### 5.1. Зачем (ситуации)

- Договор: данные физлиц и операции клуба **в РФ**.
- Доступность: меньше риска блокировок / деградации зарубежного edge для зала.
- Latency: планшеты и админы в РФ → ближе Postgres и API.
- Оплата и поддержка: счета в рублях, русскоязычный хостер.

### 5.2. Что переезжает (три куска)

| Кусок | Сегодня | Цель в РФ |
|-------|---------|-----------|
| **Статика PWA** | Vercel | Object Storage + CDN **или** App Platform (Timeweb / Selectel / Yandex Cloud) |
| **API** (`api/*.js`) | Vercel Serverless | Node (тот же код) на контейнере / VM / serverless РФ |
| **Postgres + Auth** | Supabase Cloud | Managed Postgres в РФ **+** слой Auth (см. варианты) |

**Не переезжает смысл:** IndexedDB, очередь sync, allowlist таблиц, правила абонементов. Меняются **URL и env**, не доменные правила.

### 5.3. Варианты целевой архитектуры

| Вариант | Суть | Плюсы | Минусы | Когда выбирать |
|---------|------|-------|--------|----------------|
| **C0 — Гибрид** | Фронт/API в РФ, БД пока Supabase (EU/US) | Быстрый пилот доступности сайта | Данные всё ещё не в РФ; двойная латентность | Только smoke «сайт открывается» |
| **C1 — Self-host Supabase в РФ** | Весь стек Supabase на VM/Kubernetes в РФ | Минимум правок в клиенте (`VITE_SUPABASE_*`) | Сложная эксплуатация (Auth, Realtime, Studio, обновления) | Команда готова админить Supabase |
| **C2 — Postgres РФ + свой API Auth** | Yandex/Selectel Managed PG; API как сейчас + сессии/JWT сами | Чистый контроль, проще биллинг РФ | Нужно заменить Supabase Auth / RLS-паттерны на свой слой | Долгосрок, 10+ клубов, жёсткий 152‑ФЗ |
| **C3 — BaaS в РФ** (если появится зрелый аналог) | Замена Supabase «как сервис» | Меньше ops | Зрелость, lock-in, миграция схемы | Оценивать отдельно, не блокировать C1/C2 |

**Решение владельца (2026-07-25):** целевой путь — **C2 + Yandex Cloud** (Managed PostgreSQL в РФ + Node API + слой Auth в нашем коде). Критерии выбора: минимум сисадминства (без найма админа серверов), новичок в инфре, соответствие контуру ПДн/РФ важнее цены. **C1 (self-host Supabase) отвергнут** как основной — слишком много ручной эксплуатации Docker. **C0** — только временный smoke, не цель «данные в РФ». Selectel — запасной, если Yandex не подойдёт по договору; тоже только **Managed БД**, не голый VPS.

Практично сейчас: **облако и счета — на ваше ИП**. Другие клубы (друзья/партнёры) заходят в **ваше** приложение как пользователи (свои логины тренеров/админов клуба), а не как совладельцы Yandex.

**«Правильно» с законом vs «пока между своими»**

- С точки зрения удобства разработки: один аккаунт Yandex, одна база/стенд, много клубов внутри продукта — нормальная схема.
- С точки зрения закона (очень грубо): у каждого клуба есть **свои** клиенты (персональные данные). Кто «оператор», кто «обработчик», что в договоре клуба с вами — это как раз тема юриста. Пока партнёры «не спрашивают», риск ниже на практике, но **не равен нулю**.
- Когда появится платный чужой клуб или странный вопрос — сделайте короткий договор «мы даём программу / где лежат данные / кто за что отвечает» + политика конфиденциальности на сайте. До стенда R2 это **не блокер**.

### 5.9. Стек и TypeScript vs переезд (рабочий минимум)

**Зачем секция:** не путать «подтянуть стек» с переездом и не устроить большую миграцию в худший момент. Сейчас стек под продукт зала уже уместен (JS/React, `api/_lib`, IndexedDB+sync, Supabase). TypeScript **сам** не даёт 10/10 и **не** заменяет R2–R4 / §5.7.

**Цель подтягивания:** сделать cutover **безопаснее и дешевле**, сохранив офлайн/Sync. Не цель — «весь репо на `.tsx`» или новый фреймворк.

#### Оптимальный минимум (что реально делать)

| Волна | Делаем | Не делаем | Критерий «достаточно» |
|-------|--------|-----------|------------------------|
| **R1 (сейчас)** | (1) Добивать только **пробелы** портативности. (2) Контракты: `verify-*` + при касании JSDoc/`@typedef` или мягкий TS на **push / membership / trainer-pull** (не весь UI). (3) Гигиена security без спринта §5.7. (4) Простой **baseline** Sync: время/размер pull при удобном прогоне — зафиксировать цифру, не строить платформу метрик. (5) God-файлы — **только по касанию** фичи. | Полный TS; Nest/Redis/микросервисы; оптимизация pull без метрики; security-спринт «начерно» на Vercel; второй стек «уже под Яндекс» | Контракт `/api/*` стабилен; новые таблицы = RLS + allowlist; перед фичей в sync — lint + verify/`qa:local` |
| **R2 (по команде)** | Стенд C2; Auth по [AUTH_C2_MAP.md](./AUTH_C2_MAP.md); типы/поля сессии — **только по касанию** auth; тот же сценарий зала на staging; сравнить Sync с baseline | Миграция сотен `.js`→`.ts`; смена модели sync; §5.7 и §5.8 в том же потоке | Staging = критические сценарии stability; `QA_ORIGIN=<staging>` |
| **R3 (cutover)** | Flush очередей, ярлыки PWA, мониторинг 3–7 дней, rollback | Любой «улучшим стек», TS-марафон, ускорение pull, CRM-швы | Клуб живёт на РФ; Sync и статистика без регрессии |
| **R4 + §5.7** | Rate limit / роли / админ-email на **целевом** периметре; при желании — `strict` TS и typecheck в CI **на границах API/Auth** | Смешивать hardening с недожатым пилотом | Чеклист §5.7; отдельная команда на углубление TS |

#### Очередь при конфликте (стек vs переезд)

Внутри §6 ниже — общий приоритет продукта. Для **именно** стека/TS:

1. Не сломать Sync / абонемент / завершение тренировки.  
2. Готовность и исполнение R2→R3.  
3. Контракты (verify + узкий JSDoc/TS на границах).  
4. §5.7 после стабильного пилота.  
5. Углубление TypeScript / полировка стека — **после** 1–4, не вместо.

#### Почему так (критика ложных путей)

| Идея | Почему отсекаем или сужаем |
|------|----------------------------|
| «Сначала весь TS — потом переезд» | Дорого; мало помогает DNS/Auth/PG; отвлекает от R2 |
| «TS = 10/10 стек» | 10/10 ≈ стабильный зал + РФ-периметр + security + ops; язык — малый плюс |
| «Security до cutover на Vercel» | Двойная работа; см. §5.7 |
| «Оптимизируем Sync к переезду» | Без метрики и вне окна R3 — риск регрессии; в cutover **запрещено** менять модель sync (§5.5–5.6) |
| «Параллельный стек под Яндекс» | Дубль; уже отвергнуто в §0 |

#### Связь с кодом (куда смотреть)

- Портативность: `.cursor/rules/fitness-diary-hosting-portability.mdc`  
- Sync-контракт: [SYNC.md](./SYNC.md); не менять в PR cutover  
- Auth C2: [AUTH_C2_MAP.md](./AUTH_C2_MAP.md) — реализация **только** после «стартуем R2…»  
- Проверки: `npm run lint`; sync/agg/абонементы → `qa:local` / `scripts/verify-*.mjs`  
- TypeScript в репо **пока нет** — появление = отдельный маленький шаг (мягкий `tsconfig` + `allowJs`, `typecheck` **не** ломает build на старте), не условие R2

**Триггеры кода по стеку:** явная просьба «делаем мягкий TS/JSDoc на границах» **или** касание push/pull/auth в задаче. Без этого — не стартовать миграцию «из стратегии».

- **Ситуация:** сеть из 20 клубов в разных городах РФ. **Вау:** один кабинет, данные в РФ, Sync &lt; N с на плане. **Масштаб:** шаблон «новый клуб за день». **Риск:** средний (нужен R2+).
- **Ситуация:** проверяющие / юристы спрашивают локализацию. **Вау:** одностраничный ответ «где данные и бэкапы». **Масштаб:** ускоряет B2B. **Риск:** низкий (процесс).
- **Ситуация:** ИСКРА с утра без VPN. **Вау:** бриф всегда доступен. **Масштаб:** привычка ≥3 раза/нед. **Риск:** средний (AI-провайдер).
