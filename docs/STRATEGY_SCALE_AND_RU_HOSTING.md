## 0. Ситуация → польза → развитие

### Ситуации

1. **Управляющий в 8:00** открывает админку с телефона / ноутбука клуба: нужны цифры и ИСКРА без «сайт не открылся из‑за зарубежного хостинга».
2. **Тренер в зале** на планшете без стабильного Wi‑Fi: тренировка пишется офлайн; вечером Sync должен уйти в облако, которое доступно из РФ и не «заморожено» паузой Free.
3. **Собственник сети** подписывает договор: «где лежат данные клиентов? можно ли в РФ? кто бэкапит?» — без ответа сделка тормозит.
4. **Разработчик** при 5–10 клубах: лимит 12 functions, egress, медленный pull — нужна ясная очередь работ, а не «перепишем всё».

### Польза

- Продукт остаётся **офлайн-first для зала** и **цифры + действие для кабинета**.
- Инфра растёт **по триггерам**, не «на всякий случай».
- Путь на **российские серверы** понятен заранее: без сюрприза в день договора.

### Вердикт фильтра идеи

| Идея | Вердикт |
|------|---------|
| Дожать масштаб по текущему ROADMAP (клубы, Pro, фаза 4) | **Делаем** — уже в docs |
| Заложить стратегию РФ-хостинга + правило портативности | **Делаем** — этот документ + `.cursor/rules/fitness-diary-hosting-portability.mdc` |
| Учитывать портативность в каждом PR (env, `_lib`, без lock-in) | **Делаем сейчас** — без cutover |
| Сразу переезжать с Vercel/Supabase | **Отложить** — этапы R2–R4 только по явной команде |
| Параллельно строить второй стек «с нуля» | **Не делаем** — дубль и риск sync |

## 1. Как устроены лучшие программы «нашего класса»

FIT-CITY ближе не к «сайту клуба», а к связке:

- **Планшет в зале** (как POS / field app): офлайн-запись, очередь, синхронизация.
- **Кабинет сети** (как HQ SaaS фитнеса: Mindbody / Glofox / Trainerize по духу): роли, отчёты, задания, AI-советник.

| Принцип у лидеров | Что это значит на практике | У нас сейчас |
|-------------------|----------------------------|--------------|
| **Офлайн-first на точке** | Пишем локально; сеть — бонус | ✅ IDB + `sync_queue` + flush→pull |
| **Облако = источник правды** | Конфликт: pending не затираются pull | ✅ `putStoreUnlessPendingSync` |
| **Тонкий UI, толстый домен** | Правила в сервисах, не в JSX | ✅ частично; strangler god-файлов ongoing |
| **Мульти-тенант по клубу** | `club_id`, RLS, изоляция | ✅ клубы + RLS; supervisor ещё ТЗ |
| **Один API-шлюз** | Мало entrypoints, много actions | ✅ `admin-data?action=` (лимит Hobby) |
| **Агрегаты, не «грузи всё»** | Stats/RPC при росте | ✅ Node agg + verify; SQL RPC — фаза 4 |
| **Наблюдаемость** | Логи, алерты, smoke на prod | ✅ weekly smoke; Sentry — по согласованию |
| **Регион данных рядом с клиентом** | Latency + договор + устойчивость | ⏸ сейчас US SaaS (Vercel + Supabase) |
| **Платёжный / юр. контур региона** | Счета, 152‑ФЗ, поддержка | ⏸ продукт готов; инфра — план §5 |
| **Деплой без боли** | Preview, rollback, чеклист | ✅ `qa:local`, RELEASE; домен свой — опционально |

**Вывод:** по архитектуре продукта мы уже на стороне «взрослых» офлайн+SaaS. Главный разрыв с лидерами рынка РФ — **не фичи зала**, а **регион хостинга, договорная зрелость инфра и операционный масштаб 5–10+ клубов**.

## 3. Целевая картина (12–24 месяца)

Один продукт, три опоры:

```
Планшет (офлайн)  →  API + Postgres (регион РФ)  →  Админка / ИСКРА / продажи
```

1. **Зал** — как сейчас: минимум тапов, Sync по кнопке, понятные ошибки на русском.
2. **Сеть** — 5–10 клубов на одном контуре с бэкапами и мониторингом.
3. **Инфра** — данные и API в РФ (или гибрид на переходный период); фронт с CDN в РФ.

Не цель «переписать под микросервисы». Цель — **тот же контракт sync**, другой адрес серверов.

## 5. Трек: переход на российские серверы

### 5.1. Зачем (ситуации)

- Договор: данные физлиц и операции клуба **в РФ**.
- Доступность: меньше риска блокировок / деградации зарубежного edge для зала.
- Latency: планшеты и админы в РФ → ближе Postgres и API.
- Оплата и поддержка: счета в рублях, русскоязычный хостер.

### 5.2. Что переезжает (три куска)

| Кусок | Сегодня | Цель в РФ |
|-------|---------|-----------|
| **Статика PWA** | Vercel | Object Storage + CDN **или** App Platform (Timeweb / Selectel / Yandex Cloud) |
| **API** (`api/*.js`) | Vercel Serverless | Node (тот же код) на контейнере / VM / serverless РФ |
| **Postgres + Auth** | Supabase Cloud | Managed Postgres в РФ **+** слой Auth (см. варианты) |

**Не переезжает смысл:** IndexedDB, очередь sync, allowlist таблиц, правила абонементов. Меняются **URL и env**, не доменные правила.

### 5.3. Варианты целевой архитектуры

| Вариант | Суть | Плюсы | Минусы | Когда выбирать |
|---------|------|-------|--------|----------------|
| **C0 — Гибрид** | Фронт/API в РФ, БД пока Supabase (EU/US) | Быстрый пилот доступности сайта | Данные всё ещё не в РФ; двойная латентность | Только smoke «сайт открывается» |
| **C1 — Self-host Supabase в РФ** | Весь стек Supabase на VM/Kubernetes в РФ | Минимум правок в клиенте (`VITE_SUPABASE_*`) | Сложная эксплуатация (Auth, Realtime, Studio, обновления) | Команда готова админить Supabase |
| **C2 — Postgres РФ + свой API Auth** | Yandex/Selectel Managed PG; API как сейчас + сессии/JWT сами | Чистый контроль, проще биллинг РФ | Нужно заменить Supabase Auth / RLS-паттерны на свой слой | Долгосрок, 10+ клубов, жёсткий 152‑ФЗ |
| **C3 — BaaS в РФ** (если появится зрелый аналог) | Замена Supabase «как сервис» | Меньше ops | Зрелость, lock-in, миграция схемы | Оценивать отдельно, не блокировать C1/C2 |

**Рекомендация по умолчанию для FIT-CITY:** идти к **C1 как MVP переезда** (сохраняем контракт клиента), параллельно держать в уме **C2**, если self-host Supabase окажется тяжёлым в поддержке. **C0** — только временный мост, не цель договора «данные в РФ».

#### §5.4.1 Инвентарь внешних зависимостей (R1)

| Зависимость | Где сейчас | Что переносить при РФ |
|-------------|------------|------------------------|
| **Статика PWA** | Vercel | Object Storage / App Platform + CDN |
| **API** `/api/*` | Vercel serverless (`api/*.js` + `_lib`) | Тот же Node-контракт на РФ |
| **Postgres + RLS** | Supabase Cloud | C1: self-host Supabase **или** C2: Managed PG |
| **Auth** (логин, сессия) | Supabase Auth + `/api/auth-sign-in`, `/api/me-profile` | Site URL / Redirect на новый origin; при C2 — свой слой |
| **Service role** | `SUPABASE_SERVICE_ROLE_KEY` на API | Тот же секрет на новом хосте |
| **Edge Functions** | `create-trainer`, `delete-trainer`, (legacy) `gemini-analytics` | До cutover: убедиться, что create/delete покрыты `/api/*` или задеплоить Edge в РФ |
| **Gemini** | `GEMINI_API_KEY` → `admin-data?action=gemini-analytics` | Проверить доступ из РФ; ключ в env API |
| **Web Push** | `VAPID_*` на API; клиент с того же origin | Новые ключи ок; origin сменится → пользователи заново разрешают уведомления |
| **Prod smoke** | `QA_ORIGIN` (дефолт `fitness-diary-bice.vercel.app`) | Сменить env на новый URL |

**Ок оставить хардкод до переезда:** docs (RELEASE, RUNBOOK, handoff) с текущим prod URL; дефолты `QA_ORIGIN` / dev-proxy — это «адрес сегодняшнего боя», не бизнес-логика.

### 5.5. Риски и как снижаем

| Риск | Снижение |
|------|----------|
| Потеря pending на планшетах при смене URL | Сначала flush очереди на старом API; смена origin только после пустой очереди / инструкции залу |
| Расхождение Auth | Чеклист ролей `qa:roles`; один Site URL |
| Edge Functions не переехали | Включить create/delete trainer в том же API-контуре РФ **до** cutover |
| Gemini недоступен из РФ | Прокси/ключ/запасной провайдер; ИСКРА деградирует мягко, зал не блокируем |
| Долгий простой | R2 полный стенд; R3 blue-green; окно ночью |
| «Перепишем sync заодно» | **Запрещено** в том же PR, что cutover |

### 5.6. Что сознательно не делаем в первом переезде

- Смена модели sync (CRDT, realtime-everywhere).
- Разбиение на микросервисы.
- Новый UI «под новый хостинг».
- Одновременный запуск 10 клубов на сыром РФ-стенде без R2.

## 9. Wow / масштаб (не в этом документе как scope)
