# Домен оплат (платёж) — ТЗ

**Актуально:** 2026-08-05  
**Статус:** 📋 ТЗ (код и миграции ещё нет). Слой **L3** до кассы — сначала правда в Оси.  
**Цель продукта:** замена 1С в ежедневной операционке + CRM в Оси — [PRODUCT_VISION.md](./PRODUCT_VISION.md) §2, §7.4.  
**Сейчас (мост):** импорт `31.xlsx` → агрегаты дня (`club_sales_daily`); строки оплаты **не** хранятся. Цена на абонементе — `memberships.paid_amount` (**не** платёж).

**MVP залов:** сначала **ПЗ и АЗ** (ниже §3a). **ТЗ** и `dop` — в той же модели полями, но сценарии CRM/UI и вычитка Excel для них — вторая очередь.

Онбординг залов: [PZ_CLIENTS_ONBOARD.md](./PZ_CLIENTS_ONBOARD.md) · [AZ_CLIENTS_ONBOARD.md](./AZ_CLIENTS_ONBOARD.md).

## 1. Ситуация → польза

| Ситуация | Сейчас | С доменом платежа |
|----------|--------|-------------------|
| Вечер: менеджер сводит день | Каждый раз грузит Excel из 1С | Факты уже в Оси → день = сумма строк (или сверка) |
| «Кто заплатил / за какой зал» | Только в файле | Список платежей в клубе за дату |
| Карточка / стратегия / ИСКРА | Косвенно через отчёт и абон | Связь платёж ↔ клиент ↔ абон |
| Касса (облако / железо) | Не к чему стыковать | Адаптер пишет **тот же** факт оплаты |

**Вердикт:** **Делаем** (модель → потом касса). Без сущности оплаты Excel цементируется навсегда.

## 3. Сущность `payment` (канон Оси)

Логическая запись **одного факта оплаты** в клубе. Вендор кассы / колонки Excel — только в адаптере.

### Обязательные поля (MVP)

| Поле | Смысл |
|------|--------|
| `id` | uuid |
| `club_id` | клуб |
| `paid_at` / `payment_date` | дата (день клуба; время — опционально) |
| `amount` | сумма ₽ (> 0) |
| `hall` | `pz` \| `tz` \| `az` \| `dop` (доп. продажи) |
| `segment` | `nk` \| `dk` \| `uk` \| null (пока не разметили) |
| `source` | `manual` \| `import_1c` \| `cash_cloud` \| `cash_device` (позже) |
| `created_at` / `updated_at` | аудит |
| `created_by` | user id (если есть) |

### Желательные (сразу закладываем, nullable)

| Поле | Смысл |
|------|--------|
| `client_id` | клиент в Оси (если сопоставили) |
| `membership_id` | абон, к которому относится оплата |
| `card_number` | нормализованный № карты (поиск / импорт) |
| `external_ref` | id чека / строки 1С / id провайдера (идемпотентность) |
| `note` | короткая пометка |
| `voided_at` | мягкая отмена (не удалять историю) |
| `az_direction_type_id` | только для `hall = az` — тип/направление на момент оплаты (nullable) |

**Не в MVP:** фискальный номер «на глаз», НДС-схемы, DDS, разнесение по статьям бухгалтерии.

### Правила

1. **Одна правда** — отчёт дня и ИСКРА опираются на сумму/`segment`/`hall` из платежей (или на явный override дня — см. фазу B).
2. **Адаптер ≠ домен** — парсер 1С и webhook кассы мапят в канон; UI и agg не знают имён колонок Excel.
3. **`paid_amount` на membership** остаётся ценой пакета; платёж может ссылаться на membership, но не заменяет поле.
4. **Идемпотентность** — повторный импорт той же `external_ref` + `club_id` не плодит дубли.
5. **Роли** — писать: admin / sales_manager своего клуба; читать: те же + (позже) supervisor. Service role только через `/api/*` с auth.
6. **Списание занятия АЗ / тренировка ПЗ ≠ платёж** — это расход услуги; деньги — отдельная строка `payment`.

## 3a. MVP: сначала ПЗ и АЗ

Почему эти два: уже сильная CRM в Оси (lite/клип/desk, списания АЗ, карточки из оплат); ежедневная боль — деньги из `31.xlsx`. ТЗ desk тоже важен, но абон там проще (только срок) — подключаем тем же `hall = tz` во второй очереди UI/сценариев.

### ПЗ (`hall = pz`)

| | |
|--|--|
| **Кто клиент** | С `trainer_id` (полный дневник или lite); не `desk_hall` |
| **Ситуация** | Продали персональный абон → вечером сумма в отчёте; карточки без клиента — «ПЗ без карточки» |
| **Мост сейчас** | `31.xlsx` → форма дня + блок карточек → lite / клип ([PZ_CLIENTS_ONBOARD.md](./PZ_CLIENTS_ONBOARD.md)) |
| **Цель** | `payment` (сумма, сегмент, карта) → при необходимости тот же flow создания клиента/абона; день = Σ платежей ПЗ |
| **Связи** | `client_id`, `membership_id`; тренер на клиенте, не на платеже |
| **Не путать** | Завершение тренировки / списание лимита ПЗ — не создаёт `payment` |

**Критерий для ПЗ:** менеджер видит оплаты ПЗ за день в Оси и может завести/привязать карточку **без** обязательного Excel (файл — догонка).

### АЗ (`hall = az`)

| | |
|--|--|
| **Кто клиент** | `desk_hall = az`, без тренера |
| **Ситуация** | Продали/продлили аэробный абон (направление) → деньги в дне; визиты списываются отдельно |
| **Мост сейчас** | `31.xlsx` + закрытия Excel + списания в матрицу ([AZ_CLIENTS_ONBOARD.md](./AZ_CLIENTS_ONBOARD.md)) |
| **Цель** | `payment` с `hall = az` (+ опционально направление) → привязка к desk-клиенту/абону; день = Σ платежей АЗ |
| **Связи** | `client_id`, `membership_id`, `az_direction_type_id` |
| **Не путать** | «Списать занятие» пишет визит, **не** платёж; матрица шт. из списаний ≠ рубли |

**Критерий для АЗ:** оплаты АЗ за день в Оси; списания по-прежнему из журнала визитов; Excel закрытий — реже (сид базы, не ежедневные деньги).

### ТЗ и доп. (`tz` / `dop`) — очередь 2

Поле `hall` уже в каноне. Agg дня считает все залы. Отдельные сценарии «карточки из оплат» / онбординг ТЗ и ручной ввод `dop` — после стабильного ПЗ+АЗ.

### Agg в дневной отчёт (ПЗ/АЗ в MVP)

Из не-void платежей за `payment_date` + `club_id`:

- `profit_nk|dk|uk` — сумма `amount` по `segment` (все залы MVP; ТЗ/dop если уже импортированы — тоже);
- матрица шт. — **не** из платежей автоматически в v1 (шт. = продажи/списания как сейчас); платежи закрывают **рубли**.

Рекомендация для фазы A: **рубли из платежей; штуки матрицы — как сегодня** (ручной ввод / импорт галочек / списания АЗ), чтобы не сломать отчёт. Зафиксировать в verify.

## 4. Фазы внедрения (без большого взрыва)

| Фаза | Что | Касса | Excel |
|------|-----|-------|-------|
| **A — модель + verify** | Нормализация строки; идемпотентность; agg **рублей** дня; кейсы **ПЗ и АЗ** в verify | нет | ещё мост |
| **B — хранение** | Таблица Postgres; импорт пишет строки (приоритет hall pz/az) | нет | dual-write |
| **C — UI** | Список платежей дня с фильтром ПЗ \| АЗ; ручной ввод | нет | файл опционален |
| **D — касса** | Адаптер облако → тот же `payment` | да | редко |
| **E — железо** | Физ. касса | да | — |

Критерий «вышли из ежедневной 1С» для MVP: день по **ПЗ и АЗ** закрывается без обязательного `31.xlsx`.

Код (когда начнём): `src/lib/admin/payment*Core.js` + `api/_lib/` + `scripts/verify-payments-*.mjs`; тонкий `admin-data?action=payments` (лимит Hobby).

## 5. Связь с текущим импортом

Сегодня: строки Excel → `buildDailyFormFromPaymentLines` → поля формы → Save в `club_sales_daily`.

Цель после B:

```
Excel / ручной ввод / касса
        ↓ адаптер (pz / az в приоритете сценариев)
   payment rows (канон)
        ↓ agg рублей (verify)
   club_sales_daily + «Карточки из оплат» (ПЗ / АЗ)
```

«Карточки из оплат» остаются: CRM (клиент/абон), не замена ledger.
