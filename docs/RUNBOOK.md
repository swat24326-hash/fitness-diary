# Runbook: типовые инциденты

Краткие действия для поддержки клуба. **История кейсов и классификация** — [INCIDENTS.md](./INCIDENTS.md) (контуры, коды A–Q, INC-*); ведёт агент по чату.

Код и архитектура: `.cursor/rules/`, `docs/PROJECT_HANDOFF_FOR_AI.md`.

## 0. Админ: иконка «Сбои устройств» в шапке

Красная цифра на иконке-мониторе (или push «Сбой планшета») — у тренера серьёзная проблема на планшете. Звонка от тренера ждать не нужно.

1. Нажать иконку → карточка в «Требуют внимания»: что сломалось и **что сказать тренеру**.
2. **Написать тренеру** — откроется чат с готовым текстом; или **Скопировать** и отправить в мессенджер / голосом.
3. Тренер выполнил шаги → карточка уйдёт сама при следующем отчёте планшета (до 5 мин). Если проблема известна и ждёт разработчика — **Решено** (вернётся, только если добавится новый сбой).
4. Не помогло за 30 мин → скрин карточки разработчику. У тренера при сбое в шапке появляется значок **«Помощь»** — там тот же журнал ошибок.

Подробно: [DEVICE_HEALTH.md](./DEVICE_HEALTH.md). Диагностика своего ПК админа — там же, внизу: «Это устройство».

## 1. Sync «висит» / бейдж не сходит

**Симптомы:** долго «Синхронизация…», число в очереди не уменьшается, тренировки не появляются в облаке.

**Проверить:**

1. Сеть на планшете (Wi‑Fi / мобильный интернет).
2. **Помощь → Диагностика** (если доступно): очередь, последние ошибки sync.
3. Выйти и войти снова (сессия 401 даёт retry, не «успех»).

**Действия тренера/админа:**

- Не удалять приложение с планшета без инструкции разработчика (потеря несинхронизированной очереди).
- Нажать **Sync** один раз, подождать 1–2 минуты, не спамить кнопку.
- Обновить PWA (баннер «Обновить» или перезагрузка вкладки).

**Разработчик:**

- Смотреть журнал: 403 по клиенту → запись должна сниматься с очереди (`markRecordSynced`), не копиться бесконечно.
- 5xx / сеть → записи остаются, повтор при следующем Sync.
- **HTTP 400 `memberships` / `start_date` null:** локально ушла правка абонемента с пустой датой начала. После деплоя API (`normalizeMembershipPushPayload`) update с null-датами проходит (даты опускаются). Временный обход до деплоя: открыть клиента → абонемент → указать даты → Сохранить → Sync.
- **SMS журнал пустой / нет отметок между устройствами:** таблица `club_sms_log` на prod уже есть (миграция `20260723010000`). Для ошибок в журнале нужна ещё `20260813210000_club_sms_log_status.sql` (`status`, `error_message`). Если журнал всё ещё пустой — смотреть `log_warning` / `logs_error` в ответе SMS и RLS; отправка без журнала возможна только при ошибке записи лога.
- **Журнал звонков / «Позвонить» не работает:** таблица `club_call_log` — `npm run db:migrate:club-call-log -- --linked`. Исход (длительность/отвечен) — `npm run db:migrate:club-call-outcome -- --linked` + `MOIZVONKI_WEBHOOK_SECRET` и `node scripts/subscribe-moizvonki-call-webhook.mjs`. Android клуба онлайн; тот же аккаунт Мои Звонки, что для SMS. «Команда ушла» ≠ дозвон. Короткие «пропущенные» на телефоне — Android/оператор; после webhook в журнале будет «Короткий · N с». Подробнее: [MOIZVONKI_SETUP.md](./MOIZVONKI_SETUP.md).
- После фикса на prod — один тест: офлайн → завершить тренировку → online → Sync.

## 1b. «Активные 0», а в Архиве клиенты есть (планшет тренера)

**Симптомы:** список живых клиентов пропал после перехода Архив → Активные; Sync/обновление возвращает список. Чаще при слабом интернете.

**Причина (исправлено в сборках после 2026-08):** pull архива ошибочно чистил живых из локального кэша. См. [SYNC.md](./SYNC.md) §«Архив на планшете».

**Действия:** Sync в шапке или обновить страницу. На актуальной сборке список не должен пропадать; если «Активные 0» при ненулевом Архиве — приложение само подтянет живых при возврате на вкладку.

**Симптомы:** тренер нажала «Закончить» — на планшете статус «Завершена»; зарплата за день 0 ₽; с другого устройства в карточке клиента виден **Черновик**.

2. Если на компе всё ещё черновик — открыть эту тренировку на планшете → **Сохранить** → снова Sync.
3. Обновить карточку / профиль на компьютере — должна стать «Завершена», ЗП подтянется с сервера.

**Разработчик:** INC-2026-09-09-01, [SYNC.md](./SYNC.md) §12c.

## 2. «N записей на устройстве» / пугающий журнал

**Симптомы:** бейдж или журнал показывает десятки «несинхронизированных», хотя в зале всё в порядке.

**Частые причины:**

- Старые **403** (нет доступа к клиенту) — должны считаться архивом, не «живой» очередью (актуальные сборки).
- **Типы абонементов** после pull без `synced: true` — ложный счётчик (исправлено в актуальных релизах).
- Реально висящие `synced: false` — нужен успешный Sync или разбор в Диагностике.

**Действия:** обновить PWA до последней prod-версии → Sync → если число не падает — скрин Диагностики разработчику.

## 4. Белый экран / старая версия / цикл login при обновлении

**Причины:** кэш PWA (service worker), старая вкладка, на слабом планшете — auto-reload на `/login` до готовности сессии. Карта контура: [PWA.md](./PWA.md).

**Симптомы цикла:** форма входа ↔ главная мигает, баннер «Обновление…», обновление не заканчивается, пока не закрыть приложение.

**Действия тренера:**

1. Дождаться splash «Обновляем приложение…» или нажать **«Обновить ещё раз»** один раз (не спамить).
2. Если не помогло — **Помощь → Восстановить**, либо закрыть PWA полностью и открыть снова.
3. Ctrl+F5 / очистка данных сайта — крайний случай.

**В журнале:** `Failed to fetch … PwaUpdatePrompt-….js`, MIME `text/html` — старый chunk, не Sync. В новых сборках: анти-цикл reload + in-flight splash + hard recover (`appUpdateApplyService.js`, `viteChunkReload.js`).

**Разработчик:** `verify-app-stability.mjs` (plan + guard + in-flight). Не чинить очередь Sync из‑за этого симптома.

**Действия (актуальные сборки):**

1. Обычно обновление **применяется само** при открытии приложения (не на экране тренировки).
2. После обновления вверху появится зелёный баннер **«Приложение обновлено»** (сборка в тексте) — это подтверждение, что версия новая.
3. Если баннер «Доступна новая версия» снизу — одна кнопка **«Обновить сейчас»**.
4. **Меню → Восстановить приложение** или **Помощь → Восстановить приложение** — сессия, профиль и версия одним нажатием.
5. **Помощь / Диагностика** → **Сборка** — короткий id бандла; после деплоя разработчик сверяет с новой сборкой на сервере.
6. Точка **↑** на «Помощь» — отложено обновление; откройте Помощь и нажмите «Восстановить».
7. В dev SW отключён — проблема только на **production**.

**После обновления «Клуб: …», очередь «Загрузка…», клиенты не грузятся, конверт и чат работают** (или жёлтая плашка «Данные на планшете не открываются»): новая версия обновляет базу на планшете и ждёт, пока закроется старая копия приложения. Закрыть **все** вкладки и окна приложения — в Chrome тоже (смахнуть из недавних), открыть приложение снова. Данные и очередь на планшете при этом не теряются; очищать данные сайта **не нужно**. Кейс: INC-2026-10-14-01.

## 4b. Таймаут входа / статистика «с устройства (IndexedDB)»

**Симптомы:** на логине `timeout` / «облако не отвечает»; в админке статистика пишет **с устройства (IndexedDB)** и нули по тренировкам; Sync не тянет данные.

**Причина (часто):** приложение на ВМ или база (Managed PG) не отвечает. Это не баг очереди на планшете — тренировки сохраняются локально и уйдут при следующем Sync.

**Проверить:**

1. Пришло ли сообщение сторожа в ВК «НЕ РАБОТАЕТ» — тогда действия по §9.
2. `https://app-core.ru/api/health` в браузере — `ok: true` значит сервер жив.
3. С другой сети (мобильный интернет без Wi‑Fi клуба) — повторить вход.

**Разработчик:** `journalctl -u os-hybrid -n 100`; при зависшей базе — консоль Yandex Cloud → кластер `os-c2-staging`. Verify входа: `node scripts/verify-auth-sign-in-fast-path.mjs`. После восстановления — Sync, статистика должна перейти на **из облака**.

## 4d. Консоль: «Нет сессии» / password 400, пока ещё на главной

**Симптомы:** главная тренера открыта, в консоли `[trainer-stats] … Нет сессии` и иногда `POST …/token?grant_type=password 400`. После выхода/входа — тишина.

**Причина:** в localStorage остались «токены», UI рисует профиль из кэша, а живого JWT уже нет (истёк refresh). Статистика бьёт API без Bearer.

**Действия:** выйти и войти снова. На актуальных сборках мёртвая сессия сбрасывается на логин после неудачного refresh (не остаёмся «призраком» на главной).

## 4e. Тренер: «Это устройство ждёт разрешения администратора»

**Когда:** привязка устройств включена (`DEVICE_BINDING_SINCE` на сервере). У тренера одно разрешённое устройство; вход с второго планшета / телефона ждёт админа. Админу приходит пуш «Новое устройство тренера», на главной админки — красная плашка.

**Действия админа:** «Устройства тренеров» (`/admin/devices`) → в блоке «Ждут разрешения»:

- **Разрешить** — второе устройство в дополнение к первому (например, запасной планшет зала).
- **Заменить** — новый планшет вместо старого: старый сразу теряет вход (несинхронизированное на старом останется на нём — сначала Sync, если он ещё жив).
- **Отклонить** — не пускать. Повторная попытка тренера снова попадёт в «Ждут».

Потерян / украден планшет — в списке разрешённых **Отозвать**: вход и продление с него закрываются сразу.

**Телефон тренера** (`/coach`, значок телефона в списке) — отдельно от планшета: **первый телефон тренера входит сам** (админу — пуш «Тренер подключил устройство»), каждый следующий ждёт «Разрешить» (и при входе по QR с планшета: меню → «Настройки» → «QR для телефона»). «QR-код устарел» — на планшете открыть QR ещё раз. Разрешили новый — прежний телефон тренера сразу выходит; планшет не трогается. Тренер сменил телефон — «Разрешить» новый, старый отключится сам. Потерян — **Отозвать**. [COACH_APP.md](./COACH_APP.md)


**«Обновите приложение»** у тренера — старая версия PWA без номера устройства (после первой недели). Обновить страницу / переустановить ярлык (§4).

## 5. Статистика «не сходится»

**Разделить:**

| Что | Период |
|-----|--------|
| Карточки сводки (клиенты, проведено, не активные) | **Период сводки** сверху |
| «Итог по клубу» (график по месяцам) | **Весь календарный год**, не режется периодом |

**Не активные** — на **конец периода**, с причиной (тренировки закончились, срок, не начался, нет абонемента).

**Итог по типам карт** — только тренировки с **типом карты** на абонементе; «Без типа» в годовой итог не входит.

**Дневник показывает абонемент, журнал — «Без типа»:** раньше разная логика; с 2026-08 — общий fallback по дате (`membershipTypeStatsAgg` + `trainingMembershipLinkCore`). Sync **не** лечит пустой `membership_type_id` на абонементе — правка в карточке клиента. Тренер в консоли **403 на list-memberships** — ошибка конфигурации клиента (тренер должен использовать `trainer-pull`); см. [SYNC.md](./SYNC.md) §«Тип карты», [API.md](./API.md).

## 8. Пропали или испортились данные клуба (восстановление из копии)

Решает разработчик вместе с владельцем — восстановление перезаписывает текущие данные. Сначала остановить ущерб: понять, что именно пропало и с какого времени.

1. **Точечно (одна таблица / клиент):** взять ночную копию с ВМ `/var/backups/fitness-diary/daily/fd-<дата>.dump` и достать нужное в отдельную базу/файл: `pg_restore --data-only --table=<таблица> -f out.sql fd-<дата>.dump` — затем вернуть строки вручную. Прод не трогаем целиком.
2. **Весь кластер на момент времени (< 7 дней):** консоль Yandex Cloud → Managed PostgreSQL → `os-c2-staging` → Резервные копии → «Восстановить» в **новый** кластер, проверить данные, затем переключить `DATABASE_URL` на ВМ. Действие в консоли — задача GrokBot `danger` с «да» владельца.
3. **Сервер (ВМ) пропал или копии на нём испорчены (< 30 дней):** зашифрованные копии в бакете `PG_BACKUP_BUCKET` (`daily/fd-<дата>.dump.gpg`). Скачать (консоль Yandex Cloud → Object Storage), расшифровать паролем владельца: `gpg -d -o fd.dump fd-<дата>.dump.gpg`, дальше как в п.1. Проверка, что это работает, — ежемесячно сама (`scripts/pg-restore-drill-vm.sh`, строка «Пробное восстановление» в утренней сводке ВК).
4. **Аккаунт Yandex Cloud недоступен целиком:** еженедельная зашифрованная копия на ноутбуке владельца `C:\fd-backups\fd-<дата>.dump.gpg` (8 недель, `scripts/pg-backup-pull-laptop.ps1`, журнал `pull.log`) — расшифровать тем же паролем, дальше как в п.1 на любом PostgreSQL 16. Временно, до своего второго сервера.
5. **Старше 30 дней** — только выгрузка Supabase на 30.09 (`/var/backups/fitness-diary/r4-supabase-2026-10-07/`, gzip NDJSON), пока проект Supabase на паузе.

Перед восстановлением: Sync на планшетах до пустой очереди, иначе свежие записи тренеров потеряются.

## 9. Пришло сообщение ВК «НЕ РАБОТАЕТ» / сводка «ЕСТЬ ПРОБЛЕМЫ»

Пишет сторож на ВМ (`scripts/ops-alerts-vm.mjs`): проверка раз в минуту, тревога после двух неудач подряд, напоминание раз в 30 мин, «ВОССТАНОВИЛОСЬ» с длительностью простоя; сводка за сутки — в 06:00 МСК.

| Сообщение | Что значит | Первое действие |
|---|---|---|
| приложение на сервере | процесс `os-hybrid` не отвечает | разработчику: `journalctl -u os-hybrid -n 100`, `systemctl restart os-hybrid` |
| сайт снаружи (приложение работает) | Caddy, сертификат или DNS | `systemctl status caddy`, `journalctl -u caddy -n 50` |
| база данных | Managed PG недоступна | консоль Yandex Cloud → кластер; тренеры продолжают офлайн, Sync догонит |
| место на диске | занято ≥ 95% | старые копии в `/var/backups/fitness-diary/`, журналы `journalctl --vacuum-size` |
| «Копия базы: СВЕЖЕЙ НЕТ» | ночной `pg-backup` упал | `journalctl -t fd-pg-backup --since -2d`, запустить `sudo bash scripts/pg-backup-vm.sh` |
| «Копия в хранилище: НЕ УШЛА» / «Пробное восстановление: НЕ ПРОШЛО» | бакет, права или пароль шифрования | `journalctl -t fd-pg-backup -t fd-pg-restore-drill --since -2d`; вручную `sudo bash scripts/pg-restore-drill-vm.sh` |
| «Источники обновлений: не обновлялись N дн.» | `apt-get update` падает (источник Caddy / Node отвечает ошибкой) — обновления безопасности не приходят | `sudo apt-get update` — какой источник с ошибкой; временный сбой — пройдёт сам, долгий — сменить источник |
| «Обновить вручную ночью: caddy … → …» / «нужна ночная перезагрузка ВМ» | справка, не авария: Caddy и Node сами не обновляются; Ubuntu ждёт перезагрузки после обновления | ночью, когда зал пуст: `sudo apt-get install --only-upgrade caddy`, `caddy validate --config /etc/caddy/Caddyfile`, проверить сайт; перезагрузка ВМ — ~1 мин простоя, только с «да» владельца |
| «проверка снаружи: сайт не отвечает снаружи» (без сообщений сторожа ВМ) | ВМ лежит целиком или сеть до неё | консоль Yandex Cloud → Compute → `os-hybrid-staging`: статус; при Stopped — запустить (задача GrokBot) |

Залу при «НЕ РАБОТАЕТ» ничего делать не нужно: тренировки сохраняются на планшете и уйдут при следующем Sync. Внешняя проверка — функция Yandex Cloud `app-core-uptime` ([RELIABILITY_PLAN.md](./RELIABILITY_PLAN.md) 2b); при сбое всего Yandex Cloud молчат обе. Журнал сторожа: `journalctl -t fd-ops-alerts`.

## 10. Голосовые в переписке

Звук голосовых лежит сутки в бакете Object Storage ([CHAT.md](./CHAT.md) § «Голосовые сообщения»).

| Симптом | Что значит | Действие |
|---|---|---|
| В поле сообщения нет 🎤 | на сервере не задан `CHAT_VOICE_BUCKET` | настроить бакет (ниже) |
| «Голосовые пока недоступны» при отправке | то же, или бакет пропал | настроить бакет; `journalctl -u os-hybrid \| grep chat-voice` |
| «Не получилось отправить голосовое» | бакет не принял файл (права, сеть) | `journalctl -u os-hybrid \| grep '\[chat-voice\]'` — код ошибки; проверить права сервисного аккаунта |
| «Голосовое удалено через сутки» | норма: звук хранится 24 ч | — |
| «Расшифровка пока недоступна» | нет роли `ai.speechkit-stt.user` у `iskra-llm` или не настроен Яндекс для ИСКРЫ | выдать роль (задача GrokBot) |
| Нет скрепки 📎 / «Фото и файлы пока недоступны» | фото и PDF лежат в том же бакете (`voice/att/…`) — бакет не настроен | как для голосовых; `journalctl -u os-hybrid \| grep '\[chat-attach\]'` |
| «Фото удалено через сутки» / «Файл удалён через сутки» | норма: вложения хранятся 24 ч | — |
| «Фото профиля пока недоступно» в «Мой профиль» | фото лежат в том же бакете (`avatar/…`, навсегда) — бакет не настроен | как для голосовых; `journalctl -u os-hybrid \| grep '\[avatar\]'`. Правило удаления «через сутки» на префикс `avatar/` **не** ставить |
| Нет 📹 по касанию 🎤 | телефон не умеет снимать видео в браузере (старый iOS) или бакет не настроен; мышью на компьютере — только голосовые, это норма | обновить iOS; бакет — как для голосовых |
| «Нет доступа к камере» | человек нажал «Запретить» | iPhone: Настройки → Safari → Камера → «Разрешить»; Android: замок в адресной строке → Камера |
| Кружок «не загрузился» / не играет у собеседника | слабая сеть (кружок до 15 МБ, ждём 3 минуты) или WebM с Android на старом iPhone | повторить по нажатию; `journalctl -u os-hybrid \| grep '\[chat-attach\]'` |

**Первая настройка (один раз, перед деплоем голосовых):**

1. Миграции `20261020120000_chat_voice.sql`, `20261021120000_chat_voice_played.sql` (метка «прослушано») и `20261022120000_chat_voice_once.sql` (одноразовые) — `scripts/r2-pg-migrate-vm.sh` (до выкатки кода: без них переписка не загрузится — код читает колонки `voice_played_at` и `voice_once`).
2. Консоль Yandex Cloud (задача GrokBot): создать бакет (приватный, стандартное хранилище, тот же каталог), **правило жизненного цикла** — удалять объекты с префиксом `voice/` через **1 день**; сервисному аккаунту, привязанному к ВМ, — роли `storage.uploader` и `storage.viewer` на этот бакет.
3. На ВМ: `cd /opt/fitness-diary && sudo bash scripts/chat-voice-bucket-setup-vm.sh <бакет>` — пробная запись и чтение, `CHAT_VOICE_BUCKET` в `.env`, перезапуск. Откат: `.env.bak-chat-voice`.
