# Runbook: типовые инциденты

Краткие действия для поддержки клуба. Код и архитектура: `.cursor/rules/`, `docs/PROJECT_HANDOFF_FOR_AI.md`.

## 1. Sync «висит» / бейдж не сходит

**Симптомы:** долго «Синхронизация…», число в очереди не уменьшается, тренировки не появляются в облаке.

**Проверить:**

1. Сеть на планшете (Wi‑Fi / мобильный интернет).
2. **Помощь → Диагностика** (если доступно): очередь, последние ошибки sync.
3. Выйти и войти снова (сессия 401 даёт retry, не «успех»).

**Действия тренера/админа:**

- Не удалять приложение с планшета без инструкции разработчика (потеря несинхронизированной очереди).
- Нажать **Sync** один раз, подождать 1–2 минуты, не спамить кнопку.
- Обновить PWA (баннер «Обновить» или перезагрузка вкладки).

**Разработчик:**

- Смотреть журнал: 403 по клиенту → запись должна сниматься с очереди (`markRecordSynced`), не копиться бесконечно.
- 5xx / сеть → записи остаются, повтор при следующем Sync.
- **HTTP 400 `memberships` / `start_date` null:** локально ушла правка абонемента с пустой датой начала. После деплоя API (`normalizeMembershipPushPayload`) update с null-датами проходит (даты опускаются). Временный обход до деплоя: открыть клиента → абонемент → указать даты → Сохранить → Sync.
- **SMS журнал пустой / нет отметок между устройствами:** таблица `club_sms_log` на prod уже есть (миграция `20260723010000`). Для ошибок в журнале нужна ещё `20260813210000_club_sms_log_status.sql` (`status`, `error_message`). Если журнал всё ещё пустой — смотреть `log_warning` / `logs_error` в ответе SMS и RLS; отправка без журнала возможна только при ошибке записи лога.
- **Журнал звонков / «Позвонить» не работает:** таблица `club_call_log` — `npm run db:migrate:club-call-log -- --linked`. Исход (длительность/отвечен) — `npm run db:migrate:club-call-outcome -- --linked` + `MOIZVONKI_WEBHOOK_SECRET` и `node scripts/subscribe-moizvonki-call-webhook.mjs`. Android клуба онлайн; тот же аккаунт Мои Звонки, что для SMS. «Команда ушла» ≠ дозвон. Короткие «пропущенные» на телефоне — Android/оператор; после webhook в журнале будет «Короткий · N с». Подробнее: [MOIZVONKI_SETUP.md](./MOIZVONKI_SETUP.md).
- После фикса на prod — один тест: офлайн → завершить тренировку → online → Sync.

## 1b. «Активные 0», а в Архиве клиенты есть (планшет тренера)

**Симптомы:** список живых клиентов пропал после перехода Архив → Активные; Sync/обновление возвращает список. Чаще при слабом интернете.

**Причина (исправлено в сборках после 2026-08):** pull архива ошибочно чистил живых из локального кэша. См. [SYNC.md](./SYNC.md) §«Архив на планшете».

**Действия:** Sync в шапке или обновить страницу. На актуальной сборке список не должен пропадать; если «Активные 0» при ненулевом Архиве — приложение само подтянет живых при возврате на вкладку.

## 2. «N записей на устройстве» / пугающий журнал

**Симптомы:** бейдж или журнал показывает десятки «несинхронизированных», хотя в зале всё в порядке.

**Частые причины:**

- Старые **403** (нет доступа к клиенту) — должны считаться архивом, не «живой» очередью (актуальные сборки).
- **Типы абонементов** после pull без `synced: true` — ложный счётчик (исправлено в актуальных релизах).
- Реально висящие `synced: false` — нужен успешный Sync или разбор в Диагностике.

**Действия:** обновить PWA до последней prod-версии → Sync → если число не падает — скрин Диагностики разработчику.

## 3. Данные клуба не сходятся с Supabase

Полный чеклист: [SUPABASE_PROD_CHECKLIST.md](./SUPABASE_PROD_CHECKLIST.md).

**Симптомы:** в Table Editor другие клиенты/клубы, в приложении «Нон-стоп» и т.п.

**Проверить (Supabase Dashboard):**

1. **Authentication → Users** — UID админа.
2. **`public.users`** — `id` **равен** Auth UID, `role = admin`.
3. **Authentication → URL configuration** — Site URL = prod (`https://fitness-diary-bice.vercel.app`).
4. RLS: применён `supabase/policies.sql` (не только `schema.sql`).

**Не делать:** править прод только в SQL Editor без файла в `supabase/migrations/`.

---

## 4. Белый экран / старая версия после деплоя

**Причины:** кэш PWA (service worker), старая вкладка. Подробнее про установку и SW: [PWA.md](./PWA.md).

**В журнале:** `Failed to fetch dynamically imported module: …/PwaUpdatePrompt-….js`, MIME `text/html` вместо JS, или чёрный экран после деплоя — старая вкладка/кэш PWA, **не** сеть и не Sync. **Ctrl+F5**; если не помогло — очистить данные сайта для fitness-diary / переустановить ярлык PWA. В новых сборках — авто-reload + сброс SW (`viteChunkReload.js`).

**Действия (актуальные сборки):**

1. Обычно обновление **применяется само** при открытии приложения (не на экране тренировки).
2. После обновления вверху появится зелёный баннер **«Приложение обновлено»** (сборка в тексте) — это подтверждение, что версия новая.
3. Если баннер «Доступна новая версия» снизу — одна кнопка **«Обновить сейчас»**.
4. **Меню → Восстановить приложение** или **Помощь → Восстановить приложение** — сессия, профиль и версия одним нажатием.
5. **Помощь / Диагностика** → **Сборка** — короткий id бандла; после деплоя разработчик сверяет с новым JS на Vercel.
6. Точка **↑** на «Помощь» — отложено обновление; откройте Помощь и нажмите «Восстановить».
7. В dev SW отключён — проблема только на **production**.

## 4a. Выбросило на логин / «выберите клуб» у менеджера

**Симптомы:** после долгого простоя — экран входа; у менеджера продаж — «выберите клуб» / «клуб не привязан», хотя вчера работало.

**Действия (не перелогиниваться сразу):**

1. Подождать 5–10 с — идёт «Восстанавливаем сессию…».
2. **Меню → Восстановить приложение** (или Помощь → та же кнопка).
3. У менеджера на `/sales` — **Повторить**, если видите «Загружаем клуб…».
4. Админ: проверьте **клуб в шапке** — должен подставиться последний выбранный.

**Эскалация:** скрин Диагностики (сборка, кэш профиля, клуб) разработчику.

## 4b. Таймаут входа / статистика «с устройства (IndexedDB)»

**Симптомы:** на логине `timeout` или «Облако Supabase не отвечает»; в админке статистика пишет **с устройства (IndexedDB)** и нули по тренировкам; Sync не тянет данные.

**Причина (часто):** сайт на Vercel открывается, но **Supabase** (база + Auth) не отвечает или отвечает с таймаутом. Это не баг очереди на планшете.

**Проверить:**

1. [status.supabase.com](https://status.supabase.com/) — инциденты.
2. Supabase Dashboard → проект **fitness-diary** → **Restart project** (если доступно) или Pause → Resume.
3. С другой сети (мобильный интернет без Wi‑Fi клуба) — повторить вход.
4. Вход по **email** (`логин@trainer.local` или рабочий email), не только по короткому логину.

**Разработчик:** с прода `OPTIONS /api/auth-sign-in` ~0.4 с (OK), `POST` зависает → Supabase из serverless. Verify: `node scripts/verify-auth-sign-in-fast-path.mjs`. После восстановления Supabase — Ctrl+F5, Sync, статистика должна перейти на **из облака**.

## 5. Статистика «не сходится»

**Разделить:**

| Что | Период |
|-----|--------|
| Карточки сводки (клиенты, проведено, не активные) | **Период сводки** сверху |
| «Итог по клубу» (график по месяцам) | **Весь календарный год**, не режется периодом |

**Не активные** — на **конец периода**, с причиной (тренировки закончились, срок, не начался, нет абонемента).

**Итог по типам карт** — только тренировки с **типом карты** на абонементе; «Без типа» в годовой итог не входит.

**Дневник показывает абонемент, журнал — «Без типа»:** раньше разная логика; с 2026-08 — общий fallback по дате (`membershipTypeStatsAgg` + `trainingMembershipLinkCore`). Sync **не** лечит пустой `membership_type_id` на абонементе — правка в карточке клиента. Тренер в консоли **403 на list-memberships** — ошибка конфигурации клиента (тренер должен использовать `trainer-pull`); см. [SYNC.md](./SYNC.md) §«Тип карты», [API.md](./API.md).

## 6. Не создаётся клуб / «Сохраняем…» бесконечно

**Проверить:** сеть до Supabase, RLS на `clubs`, роль admin в `public.users`.

**Временно:** повторить позже; не создавать дубликаты кнопкой «Сохранить» десятки раз.

Передать:
