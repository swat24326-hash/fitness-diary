## 1. Одна фраза — какой мы продукт

**FIT-CITY — операционная система фитнес-клуба (и сети клубов):** единый контур зала, продаж, управления и учёта оплат; снаружи — сайт заявок и позже касса; сверху — доменный советник **ИСКРА** (правда в цифрах → совет → действие на планшете).

Это **не** «ещё один дневник тренировок», **не** универсальный Bitrix и **не** общий чат-бот вместо системы.

---

## 2. Зачем идём сюда (ситуации → польза)

Порядок как в фильтре идей: сначала жизнь клуба, потом развитие.

| Ситуация | Что болит без ОС | Что даёт единый контур |
|----------|------------------|-------------------------|
| Тренер в зале, слабый Wi‑Fi | Пишет в блокнот / теряет историю | Офлайн-дневник + sync без потери pending |
| Менеджер ведёт лид в Bitrix, тренер — в другой программе | Двойной ввод, воронка рвётся | Одна воронка ПНК от заявки до первой тренировки |
| Собственник утром смотрит план и риски | Excel + чаты + «универсальный ассистент» без ваших данных | Статистика + ИСКРА на **фактах клуба** + задания в приложение |
| Оплата на ресепшене и «цифры в отчёте» | Расхождение кассы и абонементов | Учёт оплат в том же продукте (позже — облачная / физическая касса) |
| Человек с телефона хочет пробную или акцию | Звонок / переписка / потеря заявки | Сайт → **заявка** (запись к тренеру или промо) → та же воронка |

**Почему Bitrix + «универсальный ассистент» недостаточно:** они не знают офлайн-зал, абонементы, качество ведения, план клуба и не доводят действие до планшета тренера. Bitrix может остаться внешним куском задач — **не ядром** FIT-CITY.

**Если не идти к ОС:** при росте клубов останется склейка инструментов; ИСКРА останется красивой надстройкой без единой правды; стоимость поддержки и ошибок будет расти быстрее фич.

## 3. Контуры продукта (входит / не входит)

### Входит в крупную цель

| Контур | Смысл | Сейчас (ориентир) | Дальше (крупно) |
|--------|--------|-------------------|-----------------|
| **Тренер (зал)** | Клиенты, тренировки, абонементы, медкарта, питание, ДЗ, офлайн | ✅ ядро в проде | Шлифовка UX, качество ведения |
| **Управление** | Статистика клуба, задания, управляющий, бриф | ✅ частично; supervisor — ТЗ | Роль управляющего, привычный утренний контур |
| **Продажи** | Менеджер, ежедневный отчёт, ПНК | ✅ в проде | Углубление воронки без второго CRM |
| **Учёт клуба** | Абонементы, продажи/план, сверка денег с залом | ✅ продажи и абонементы | Модель платежа → облачная касса → физическая касса |
| **Снаружи: сайт** | Заявка клиента: **запись к тренеру** или **фитнес-акция/промо** | ⏸ нет | Форма → сущность заявки → ПНК / запись (не ЛК клиента «как приложение») |
| **ИСКРА** | Анализ, подсказки, планёрка, доверие к цифрам | ✅ частично + north star | Сильнее по мере единой правды данных |

### Явно не входит (сейчас и в ближайших фазах)

| Не делаем | Почему |
|-----------|--------|
| Магазин мерча / футболок | Не продаём; сайт — только заявки |
| Полный ERP / замена 1С «как у завода» | Другой продукт; у нас — учёт **клуба** и оплат |
| Универсальный ассистент «про всё на свете» | Ценность — домен клуба, не общий чат |
| Bitrix как ядро данных зала | Офлайн и абонементы живут в FIT-CITY |
| Клиентское B2C-приложение «для всех» как ядро | Отдельное решение; сейчас клиент ведётся через тренера |
| Параллельный второй стек «сразу под РФ» | Портативность в дизайне; cutover — по команде, см. STRATEGY… |

## 4. Качество продукта — обязательные атрибуты

Крупная цель достигается **не скоростью фич**, а качеством системы. Каждый новый контур обязан нести те же атрибуты, что ядро зала.

| Атрибут | Что значит на практике |
|---------|------------------------|
| **Офлайн-first в зале** | Запись → IndexedDB + очередь → push; pull не затирает pending |
| **Одна правда** | Одни правила абонементов/статистики в сервисах; UI только отображает |
| **Роли и контуры** | Тренер / менеджер / админ / (позже) управляющий — разные экраны, одни данные |
| **Проверяемость** | Ветвистая логика → `scripts/verify-*.mjs` + `qa:local` на критическом пути |
| **Тонкий UI, толстая lib** | Логика в `src/lib/` и `api/_lib/`, не в god-JSX |
| **Масштаб с первого дня** | `club_id`, агрегаты, не «загрузить всё в память» без нужды |
| **Портативность хостинга** | Env, стабильный `/api/*`, без lock-in в runtime хостера (РФ — позже) |
| **Русский UX зала** | Понятные ошибки, минимум тапов, без `navigate(0)` после сохранения |
| **Фирменный стиль** | Канон Whoop-класса + ролевые оттенки; красота без вреда планшету — [BRAND_SYSTEM.md](./BRAND_SYSTEM.md) |
| **Документация как DoD** | Статус правды в `docs/`; новый модуль — строка в индексе |
| **Минимальный diff, правильный слой** | Не костыль «потом разнесём»; не рефакторинг всего подряд |

Иерархия приоритетов (если спорят цели): **стабильность зала и цифр** → архитектура и ship → экономия контекста разработки.

Фильтр новой идеи перед кодом: `.cursor/rules/fitness-diary-features.mdc` (ситуация → польза → вердикт Делаем / Упростить / Отложить / Не делаем).

## 5. Инженерное планирование (как строим путь к цели)

### 5.1. Слои доставки (не один «большой взрыв»)

Порядок слоёв согласован с зависимостями данных. Следующий слой не стартует «заодно» в том же PR без явного запроса.

| Слой | Содержание | Зависимость |
|------|------------|-------------|
| **L0 — Ядро (уже)** | Тренер, sync, абонементы, карточка, статистика, продажи, ПНК, ИСКРА v1 | — |
| **L1 — Единая операционка** | Дожать управление (supervisor), качество ведения, доверие к цифрам | L0 стабилен |
| **L2 — Внешний вход** | Сайт заявок: запись к тренеру / промо → воронка | L0 воронка ПНК |
| **L3 — Учёт оплат** | Модель платежа в домене → облачная касса → физическая касса | L0 абонементы/продажи; сверка с отчётами |
| **L4 — Сеть и инфра** | 2+ клубов, платные тарифы, при необходимости РФ-хостинг | Триггеры из GROWTH / STRATEGY |

ИСКРА усиливается на каждом слое, но **не заменяет** отсутствующую правду данных (сначала факт, потом совет).

### 5.2. Технический каркас нового контура

Перед реализацией любого из L2–L3 (и крупных кусков L1) в задаче явно фиксируем:

1. **Ситуация и MVP** — кто, когда, один главный сценарий (фильтр идей).
2. **Сущность и источник истины** — таблица/store, `club_id`, кто пишет (роль), офлайн или только онлайн.
3. **Sync / API** — нужен ли push в allowlist; новый `admin-data?action=` вместо нового `api/*.js` (лимит Hobby).
4. **Паритет правил** — если цифра в админке и на сервере: `src/lib` ↔ `api/_lib` + verify.
5. **Границы интеграции** — сайт и касса = **адаптеры** к домену FIT-CITY, не наоборот (домен не знает бренд кассы в бизнес-правилах).
6. **Риски критического пути** — не ломать завершение тренировки, абонемент, flush→pull; после касания — lint + релевантный qa/verify.
7. **Docs в той же задаче** — статус модуля, строка в [README.md](./README.md), при необходимости handoff / API / SYNC / DATA_MODEL.
8. **Не в PR** — соседний слой, wow «заодно», второй стек под другую инфру.

### 5.3. Сайт заявок (L2) — инженерный набросок

**Продукт:** публичная форма (запись к тренеру или акция) → заявка в клубе → менеджер/воронка видит её как вход в ПНК или отдельный статус «заявка с сайта».

**Не делать в MVP:** личный кабинет клиента, оплата на сайте, мерч, полноценный маркетинг-автопилот.

**Закладки в дизайн:** `club_id` / идентификатор клуба в форме; идемпотентность заявки; антиспам; без хардкода URL хостера в домене.

Детальное ТЗ — отдельный doc, когда слой L2 выбран в спринт.

### 5.4. Касса (L3) — инженерный набросок

**Продукт:** факт оплаты связан с клиентом / абонементом / продажей и участвует в сверке с отчётами и ИСКРОЙ.

**Порядок внутри L3:**

1. Доменная модель платежа (чистые функции + verify) — **без** привязки к вендору.
2. Адаптер **облачной** кассы (env, webhook/API).
3. Связь с **физической** кассой на точке (тот же доменный факт оплаты).

**Не делать в первой итерации:** полная бухгалтерия РФ, замена 1С, фискальные тонкости «на глаз» без юр. согласования.

Детальное ТЗ и выбор провайдера — когда L3 в спринте; до этого не плодить код «под кассу на всякий случай».

### 5.5. Definition of Done на пути к цели

Любой шаг к крупной цели считается сделанным только если:

- [ ] Прошёл фильтр идей (вердикт записан кратко в PR/задаче или doc)
- [ ] Код в правильном слое (`lib` / `_lib`, не раздувание god-файлов)
- [ ] `npm run lint`; на критическом пути — `qa:local` или целевой verify
- [ ] Docs обновлены (статус, индекс, контракт при смене API/sync)
- [ ] Не обещали соседний слой «заодно»

## 6. Вердикт фильтра (зафиксировано 2026-07-19)

| Идея | Вердикт |
|------|---------|
| Цель = ОС клуба (зал + продажи + управление + учёт + заявки + ИСКРА) | **Делаем** как направление |
| Строить всё одним релизом | **Упростить** → слои L0→L4 |
| Сайт = мерч | **Не делаем** |
| Сайт = заявка (запись / промо) | **Делаем** (слой L2, когда выбран) |
| Касса облачная + физическая | **Делаем** поэтапно (слой L3) |
| Bitrix / универсальный ассистент как замена ОС | **Не делаем** |
| Качество атрибутов с первого коммита каждого контура | **Делаем** — §4–5 |

## 7. Как пользоваться этим документом

1. **Новый чат / новый человек** — прочитать §1–3; детали кода — handoff.  
2. **Новая крупная фича** — сверить с §3 (входит?) и §5.1 (какой слой?); прогнать фильтр features.  
3. **Спор «Bitrix vs мы»** — §2 и «не входит».  
4. **Планирование спринта** — не смешивать L2 и L3 без явного решения; сначала правда данных, потом ИСКРА.  
5. **Обновление** — при смене типа продукта или слоёв править этот файл в той же задаче; дату «Актуально» обновить.

---

## 8. Краткая памятка для агента

- Центр продукта — **операционка клуба**, не чат и не чужой CRM.  
- ИСКРА — слой поверх **ваших** данных и действий.  
- Сайт — **заявки**, не магазин.  
- Касса — **адаптер к домену оплат**, после модели платежа.  
- Качество = sync, verify, слой, docs — не «красивый экран без правды».
